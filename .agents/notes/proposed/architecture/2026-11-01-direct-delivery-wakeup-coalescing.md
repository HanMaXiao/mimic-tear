# Agent Note: 直通的唤醒收敛 —— 在途合并，事件不丢

Status: proposed

## 问题

方案 A 落地后，「平行负责会话」的成本显出来了：**每 49 分钟被唤起 4 次**，每次都是一整轮
agent 回合——也就是每轮都面向大老板产出一份汇报（2026-11-01 15:09 实测：本会话收到的直通
注入是 06:21:42、06:50:37、07:01:23、07:09:23）。

根因是**事件源太密**：`project-activity` 的来源是**项目里的桌面会话活动**——桌面会话每干一次活
（提交、跑一次验收、查一次读数），那条线的负责会话就被唤起一轮。平行会话挂在另一个项目上，
**不自激**；但兄弟会话每在项目目录里干一次活就会再唤一次。

连带的第二个问题：**「已投出」在板面上滞后一轮回合时长**（实测 11 分钟）——`delivered` 是投递
成功之后才落盘的，而成功信号要等负责会话那一轮结束才回来。那段时间里盯盘只看得见「已投出 =
旧的」，很容易误读成「没投出去」（2026-11-01 15:09 实测：盯盘自己差点这么读）。

## 提案

**在途（in-flight）是独立的第三个状态**（在途 / 已投出 / 没投过），各管各的：

1. **投递发出即写在途标记**，不等回合结束——已落地（`08ae155`）。
2. **判定「正在处理同类事件」读在途，不读 `delivered`**：`delivered` 的窗口永远是空的
   （要等回合结束才落盘），拿它判就是**合并逻辑一行都命中不了**。
3. **命中在途时不要丢事件**：把新的活动时间戳**并进同一条在途记录**（保留「最新活动时间」），
   本轮**不投**；等那一轮结束后，**按合并后的最新值投一次**。
4. **在途标记取代「投递轮次不重叠」那个单飞闸**：单飞是钝器——一条线的长投递挡住**所有**线；
   在途标记是精确的（按项目 + 事件类型），别的线照常投递。
5. **失败路径语义不变**：投递失败 → 从在途里撤掉 → 事件下一轮还会被计划到（**失败不记账**）。

**唤醒次数的预期**：一串连续活动 → **2 次唤醒**（第一发 + 合并后的那一发），而不是每串一次。
事件不丢；负责会话拿到的是**最新**的活动时点，而不是一串历史。

## 曾考虑的替代方案

**把这条线的直通关掉**（`thread remove`）。放弃的理由：它会把刚被大老板拍板的能力整个撤掉，
而且别的线将来要用同一套机制——问题在**事件源与投递节奏**，不在「这条线该不该有投递口」。

**给平行会话换只读 agent**（`explore`）。放弃的理由：它是**权宜之计**——负责 agent 就该能干活；
它能止住「平行会话改仓库」这个风险，但止不住「每轮都产出一份汇报」这个成本。

**只把阈值调低/调高，不做合并**。放弃的理由：阈值治不了「49 分钟 4 次」——那是事件密度问题，
不是判定灵敏度问题。

## 验收标准

1. **连续 3 次活动、间隔小于一轮回合时长** → 负责会话只被唤醒 **2 次**（第一发 + 合并后的
   那一发），且最终拿到的是**最新活动时点**（不是一串历史）。
2. **在途标记在回合结束后一定转成 `delivered`**，不留悬挂——悬挂 = 那个事件永远不会被重投。
3. **失败路径语义不变**：投递失败不记账、下一轮仍可被计划到。
4. **别的线不被拖累**：一条线的长投递期间，其它线的投递照常发生（单飞闸移除后要验这一条）。
5. **测试**：走**真实模块**（`ManagedProjects` / `RuntimeStore` / `ThreadSubscriptions` / 真 CLI），
   不注入替身；「命中在途 → 合并」与「不在途 → 正常投递」两条分支都要有用例；新写的检查先做
   变异验证。

## 风险

- **合并会折叠中间状态**：负责会话只看到最新活动时点，看不到中间那几次。**这是要的效果**
  （它要的是「现在怎么样」，不是「这几分钟里发生了什么」），但要让负责人知道中间状态没了。
- **在途标记会悬挂**：负责会话那一轮永远不结束（被卡住、被中断而没 resolve）→ 在途标记一直
  在 → 那条线的投递一直被合并 → 事件一直不投。**必须给在途标记一个过期口径**（例如超过 N 分钟
  视为失效），否则一个卡死的会话能把一条线永久「合并」掉。
- **单飞闸移除后，投递轮次会重叠**：同一条线在同一时刻只允许一笔在途——这条由在途标记本身
  保证（标记是唯一的），但要验「两个 tick 同时看到没有在途标记」这个窗口。

# Agent Note: 以 Super-agent 架构作为大哥的演进基线

Status: proposed

## 问题

大哥从 2026-10-20 立起来到现在，**每一次「要不要加这个能力」都是凭直觉决定的**。

这个仓库里已经有 28 节设计规格、5 份实施计划、7 份 Agent Note，但**没有一份说清楚「大哥应该长成什么形状」**。规格记的是「已经是什么」，计划记的是「这轮做了什么」，note 记的是「某个决定为什么这么定」——**没有任何一份给出目标形态**。于是每加一个能力，都要重新论证一次「这算不算偏离」。

这个空缺在 2026-11-01 暴露出来，是因为一件具体的事：**文章《Super-agent 设计探索：迈向更自主的 Agent 系统》（DeepSeek Harness 团队，2026-10-31）**。它给出的核心判断——「单任务的上限取决于模型能力，多任务的上限取决于人的注意力」——与大老板对大哥的原始要求（「让我从『此不再开发』，主要是代替我开发任何产品，让我能抽离出来做其它事情」）**指向同一个东西**。

但把文章和我们逐条对完之后，发现差距集中在两处：

1. **组织维度。** 文章说「Session 应当是系统的实现细节，而不应是用户的认知负担」。我们的板面到今天仍**按项目组织**——用户还在替系统管理 Session。这不是实现细节，是产品形态。
2. **驱动方式。** 文章的 Super-agent 是**事件驱动**的：环境变化成为一等 Trigger，程序层先滤噪音，已建立的线由程序直通 Worker。我们的大哥是**定时轮询**的：每 30 分钟被叫醒，把全部事实重读一遍，靠模型自己判断该不该动手。

而更实际的问题是：**这篇文章是他们的架构，不是我们的问题清单。** 它假设的是云端、多信道、跨设备、团队规模。我们是本地、单宿主、单人、Mini App。**照搬会引入我们付不起的代价**——所以需要一份**基线**，而不是一份待办清单。

## 提案

**把 Super-agent 的五模块（双层架构 / 事件驱动 / 面向人的交互 / 计算-状态-环境分离 / Watchdog）与四特征（连续 / 高效 / 主动 / 持久）作为大哥演进的基线**，并配套三件事：

1. **基线规格** `docs/specs/2026-11-01-super-agent-baseline.md`——文章锚点、逐模块现状对账、四特征的可测判据、**缺口台账 G-01 ~ G-11**、**明确不照搬清单**、六道闸门。
2. **迭代计划** `docs/plans/2026-11-01-super-agent-alignment/`——三份文件（`task_plan.md` / `findings.md` / `progress.md`），六个阶段，按依赖排序。
3. **缺口台账的维护规则**——G-01 ~ G-11 是**活账本**，不是一次性清单：每落一个阶段就更新对应条目的状态；台账与规格同一次改动一起改。

**同一次决策里明确钉下的三件事：**

- **现状的诚实读数**：四特征里，**连续部分达成、高效未达标、主动未达标（且当前 `resting`）、持久运行态基本达成但恢复态不达成**。其中「恢复态不达成」指 219 个空槽 + 心跳补偿锁死——**大哥上岗前得先修这条**。
- **否决清单**：云端存算分离、端侧 daemon（BYOM）、IM/GitHub 多信道接入、Router 水平切分、跨实例 A2A、模型协同设计训练、跨月长程记忆——**七项明确不照搬**，理由逐条写进基线规格 §5。
- **不得误伤的两处**：技能库与技能工厂**不在文章的五模块里**，但它们是大哥区别于「一个派工中间人」的地方，对齐时**不许顺手删掉**。

**不在这份决策里的东西：** 任何具体能力的实现。基线只回答「朝哪长」和「什么算长到了」；实现是迭代计划的事，且每一步都要单独授权。

## 曾考虑的替代方案

**继续按项目维度迭代，不换基线。** 放弃的理由：**项目维度就是当前痛点本身**。文章点名的「Session 是用户的认知负担」，在我们的板面上就是「总览页逐个项目一张卡」。不换基线，等于每次都在症状上打补丁——把项目卡做得更漂亮、把收件箱折叠得更整齐，而「多任务上限取决于人的注意力」这件事一点没变。

**把文章当成待办清单，逐条实现。** 放弃的理由：**那七项云端/多设备设计会先炸**。「Agent Loop 部署到云端 + 端侧装 daemon」对我们意味着跨进程接管命令执行与凭据——而我们现在直接用 `mavis session send` 就够了，能力不缺，多一层 daemon 只是多一处要自己维护的东西。照搬等于**为了像一篇文章而重写一遍已经能跑的架构**。

**只借架构名词，不动组织维度。** 放弃的理由：**那是最容易自我欺骗的一种做法**——文档里写「双层架构」「事件驱动」，代码里还是按项目组织、还是每 30 分钟全量重扫。**名词到位而形状没变，比不写更危险**：它让后来的人以为这件事已经做过了。

**把这份基线写成 ADR / RFC。** 放弃的理由：**决策记录只许有一个家**——`.agents/notes/`（门禁 `scripts/verify-agent-notes.mjs` 断言 8 明确禁止 `docs/adr`、`docs/rfc`、`docs/rfcs`）。另开一家的代价是两份口径。

**把基线写进主规格 `2026-10-20-mimic-tear-design.md`。** 放弃的理由：主规格已经是 147 KB / 28 节，再塞一份演进基线进去，它就同时是「API 契约」「产品定义」「目标形态」三样东西，**读者没法判断哪段是权威**。分工改成：**主规格管「是什么」（API / 数据模型 / 事件表），基线规格管「为什么朝这个方向长」**，两边交叉链接。冲突时主规格赢。

## 验收标准

1. `docs/specs/2026-11-01-super-agent-baseline.md` 落库，含：五模块对账表、四特征可测判据、G-01 ~ G-11 台账（含依赖顺序）、七项否决清单、证据等级表、六道闸门。
2. `docs/plans/2026-11-01-super-agent-alignment/` 三份文件齐备，六个阶段的顺序与依赖与台账一致。
3. 本 note 位于 `.agents/notes/proposed/architecture/`，`Status: proposed` 与目录一致，含 `## 问题` / `## 提案` / `## 验收标准` / `## 风险` / `## 曾考虑的替代方案`。
4. `node scripts/verify-agent-notes.mjs` 通过；`node --test` 仍 **602/602 全绿**（纯文档改动，一条测试都不该变）；四道守卫脚本全绿。
5. **每个阶段收尾时**，基线规格 §4 的对应条目更新为「已落地」并写明证据位置；台账与计划 `progress.md` 同一次改动更新。

## 风险

- **文章是别人的架构，不是我们的问题清单。** 最大的风险是**基线反过来绑架实现**——为了让「对齐」而实现一批我们并不需要的能力。缓解：否决清单已经先划掉七项；**新增否决项要走同一次决策**，而不是在实现阶段临时决定「这个不用做」。
- **台账会腐烂。** G-01 ~ G-11 是 2026-11-01 的快照。三个月后再看，其中几条可能已经不成立（比如大哥若真开始管多个项目，§3.3 里「没有真实负载」那条就过期了）。缓解：台账条目**必须带状态与证据位置**，且**每个阶段收尾强制更新**（写进验收标准第 5 条）——但这条靠自觉，不靠机制，是**真风险**。
- **用外部文章给内部决策背书。** 「DeepSeek 都这么设计」容易变成不证自明的理由。缓解：基线规格里每条文章结论都**标了原文小节号**，并把文章 §8 的开放问题一并列进去——**文章自己也没解决的问题，不能拿来给我们背书**。
- **基线规格与主规格漂移。** 两份文档各有分工，但都可能被单独改动。缓解：**冲突时主规格赢**这条写在基线规格开头；G-02 ~ G-06 落地后要动主规格的 API 与事件表时，两份同一次改动一起改。
- **照搬的诱惑会反复出现。** 每读一遍文章都会觉得「这个我们也应该有」。缓解：**否决清单的每一条都写了「为什么不照搬」**，而不只是「不做」——这样下次再看到同一个想法，能直接指到理由，而不是重新论证一遍。

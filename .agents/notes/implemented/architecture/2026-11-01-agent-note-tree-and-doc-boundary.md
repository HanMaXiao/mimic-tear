# Agent Note: 决策记录树与三处文档的分工

Status: implemented

## 问题

这个仓库在 2026-11-01 之前**没有任何一份给 agent 看的常驻指令**。`.github/` 里只有一个 CI workflow；`AGENTS.md`、`CLAUDE.md`、`.cursorrules`、copilot 指令文件一个都没有。新 clone 仓库的 agent 能读到 README、规格和计划，但读不到「这个仓库的决策是怎么做出来的」。

更要命的是决策理由的**实际存放位置**和**应该存放的位置**是错位的：

- 设计规格 `docs/specs/2026-10-20-mimic-tear-design.md` 有 147 KB、28 节，里面混着产品定义、架构决策、验收标准、还有逐日追加的补记。它既是**产品是什么**的权威，也是**为什么**的半份权威——但一个 147 KB 的文件承担不了两个角色：它太长，查一条决策的成本高；它又被当作「当前事实」维护，于是**取舍过程**在不断修订中被冲淡。
- 实施计划 `docs/plans/` 下 5 份文件是**一次执行发生了什么**的记录。它们的写法是「交大哥拍板」，拍完就冻结。
- 而另有一批决策**哪儿都没写**，只活在 agent 自己的记忆里：大哥值班的三个控制开关、`patrol-cli report` 的交班戳副作用、技能工厂要同时改三个落点。这些是恰恰最容易被下一个 agent 踩中的知识，却完全不在仓库里。

`deepseek-harness` 用 `.agents/notes/` 解决了这个问题：一份份 Agent Note 记「为什么这么定、放弃了什么」，路径编码状态，机器守格式。这个仓库需要同一套机制，但**不能照抄**——它有 1800 多份 note、双语配对、TypeScript 门禁，都是那边十年积累出来的规模。

## 决策

### 三层文档，三件事

| 位置 | 管什么 | 更新时机 |
| --- | --- | --- |
| `docs/specs/` | 产品是什么：架构、API、数据模型、验收标准 | 设计变了就改 |
| `docs/plans/` | 一次执行发生了什么：分批计划、踩坑、当时拍板 | 写完即冻结，是历史 |
| `.agents/notes/` | 一个决策为什么这么定：取舍、代价、边界、什么条件下要重新考虑 | 决策落地后随代码同步更新 |

判据是**事实还是理由**。「板面有 21 条 API 路由、12 种 SSE 事件」是事实，归规格；「为什么运行时库只读、为什么写路径只有一条」的理由归 note。

**规格已经写死的约束，不在 note 里复述。** 这条是硬边界，否则 note 会退化成规格的副本，两份一起腐烂。

### Agent Note 树

路径编码两个轴：`{生命周期}/{分类}/yyyy-mm-dd-主题.md`。

生命周期是状态，note 在 `proposed/` → `implemented/` → `rejected/` 之间移动；`archived/` 是冻结的历史快照。分类是决策的种类，取封闭集合：`feature`、`bug-fix`、`simplification`、`architecture`、`process`、`testing`。

`architecture` 与 `process` 的分界：**architecture** 说的是发布的那份源码，`process` 说的是围着源码转的工具与流程。

### 单语，不做双语配对

`deepseek-harness` 每份 note 配一份 `.zh.md` 和一份 `.i18n.yaml` 侧车（记录双语分节哈希）。本仓库**只写中文**，不做配对。

理由是本仓库本来就没有双语文档：9 份 `docs/` 全是中文，代码注释全是中文，README 全是中文。硬造双语不是「更完整的国际化」，是**凭空多出一倍需要同步的内容**，而这一倍内容换不来任何人真的会去读第二份。

代价要说明白：note 里引用的英文术语（`ProjectService`、`context.logger`、`node:sqlite`）保持英文不译，和仓库其余部分一致。

### 格式由脚本守，不靠自觉

[`scripts/verify-agent-notes.mjs`](../../../scripts/verify-agent-notes.mjs) 强制：生命周期与分类是封闭集合、文件名带日期、`Status:` 行与所在目录交叉核对、每个生命周期有必带小节、`implemented/` 里禁止提案腔标题、`## 曾考虑的替代方案` 强制存在。

机器守格式，是因为格式靠自觉必然腐烂——`deepseek-harness` 的教训是：格式规则一旦不机械执行，半年后树里就混着三种骨架。

### 边界

- `.agents/notes/` 只记**持久**的决策理由。机械性、局部的改动免写。
- 一份 note 永远不能被改成另一个决策。要改决策就写新的，两份互链。
- `implemented/` 的 note 必须**跟代码保持一致**：改了路径、名字、默认值，就在同一次改动里把 note 改对，只改事实不改决策。
- `proposed/` 的 note 不归档——不再值得做就诚实地否掉。

## 曾考虑的替代方案

**把 ADR 放在 `docs/adr/`，照搬业界习惯。** 本仓库没有这个目录，而 `docs/specs/` 已经占了「架构决策」这个位置。新建 `docs/adr/` 会造出第三份权威，`specs/` 说什么、`adr/` 说什么、`notes/` 说什么——三份口径，正是这个仓库最讨厌的东西（规格 §25 专门讲「过期的问卷不是待办」就是在收口径）。放弃它的代价是：**不熟悉 ADR 习惯的 agent 需要多读一页** `.agents/notes/README.md`。

**只补一份根 `AGENTS.md`，不建 notes 树。** 更省事。但 `AGENTS.md` 是**常驻约定**——每次开工都读；决策记录是**按需查阅**——用到才读。把 20 份决策塞进 `AGENTS.md`，等于让每次开工都背着全部历史，而其中 19 份跟当前这行代码无关。放弃它的代价是：多一个目录要认。

**照搬双语配对（英文 + `.zh.md` + 侧车哈希）。** 见上。放弃的代价：跟 `deepseek-harness` 的形态不再一一对应，跨仓库读 note 的人要适应单语。

**用 TypeScript + Vitest 写门禁，跟 `deepseek-harness` 同构。** 本仓库零第三方依赖，Mini App 运行时是裸 Node（`scripts/check-package.mjs` 强制包内不得出现 `node_modules`），装不了 Vitest。现有三个守卫脚本 `check-package.mjs` / `check-published.mjs` / `check-style.mjs` 都是纯 Node `.mjs`，门禁必须跟它们同构才不突兀。放弃的代价：门禁逻辑要自己实现，不能直接抄那边的 TypeScript。

**把 note 也做成机器可读（JSON / YAML frontmatter）。** Markdown 里的 `Status:` 行已经够门禁用了，而且 note 要读、要改、要互相链接——Markdown 的可读性和链接能力无可替代。放弃的代价：结构化查询得靠 grep。

**先不写任何 note，只把目录和门禁搭起来。** 目录空着没人知道该写什么。写了 7 份真实的 note 之后，格式才有了可对照的样本。

## 后果

**换来的**：下一个 agent clone 仓库就能读到「大哥值班怎么开关」「`patrol-cli report` 有个副作用」「技能工厂要改三个地方」这些只存在于记忆里的知识，而且**带时点**——每份 note 写明决策日期和当时的读数。决策不再随某个 agent 的会话消失。

**付掉的**：

- 仓库多了一个需要维护的目录。门禁会拦住格式漂移，但拦不住「该写而没写」。
- 门禁脚本本身要维护。`deepseek-harness` 那边因为格式规则迭代过多次，脚本跟着改过好几版。
- **归档的完整性弱于 `deepseek-harness`**：那边用「封存清单 + 逐文件哈希」锁住不可变性，本仓库只在 `Status:` 下面加一行 `Archived:` 日期就封存。这是有意的取舍——本仓库现在个位数的 note，还不值得引入哈希清单；等真的攒到需要的那天再加，届时老 note 也要补封存信息。
- 现有 `docs/specs/` 和 `docs/plans/` **原样保留，不做迁移**。它们的写法与新规范不完全一致（比如规格用「## 15. 大哥值班」而不是 `## 问题`／`## 决策`），但那是另一个体量的文档，重新组织它是一次独立的、值得单独立项的工作，不该混在「补一套 Agent 机制」里。

**不做的事**：不动 `docs/` 的任何现有文件；不引入 `docs/adr/`；不为 note 造第二份权威。

# Agent Note: 板面状态收口成一个带版本的 store —— 哪些能合、哪些不能

Status: implemented

## 问题

板面的状态散在 `liveboards/mimic-tear/` 下的十几个 json 文件里。散开的代价不是「文件多」，
是**同一件事写在几个地方，跨文件的一致性只能靠人工核对**。已经出过两次真事故：

1. **派工账的并发写毁掉记录**。`dispatches.json` 有**两个写者、两个进程**——看板的派工路径
   （`persistence.mjs`）和值班路径（`patrol-store.mjs`）——两边都做读-改-写。幂等键就在
   账里，丢一条就可能把同一条指令重投一次。
2. **`patrol-cli report` 的交班戳副作用**。这条命令做两件事：写巡检结论 **+** 重打交班戳
   （`lastRunAt`）。而这两个语义完全无关——用一条非值班结论去刷交班戳，会把一次真实的
   漏班直接抹掉（见 [交班戳副作用](../process/2026-10-30-patrol-report-duty-stamp-side-effect.md)）。

两条事故的共同形状：**「一件事」被拆在几个文件里，于是「做完一件事」不是一个原子动作。**

DeepSeek《Super-agent 设计探索》§5.1 主张「状态进数据库、计算无状态」。那条结论对我们不成立
——主规格 §2 写死了「不引入任何自建状态库」，所以收口的形态只能是**一个带版本号的原子写
store**，不是数据库。

## 决策

### 收口成一个文件、一个 store

新增 `miniapp/node/board-state.mjs`：`BoardStateStore`。板面自己写的那几本账搬进**一个文件**
（`board-state.json`）里的几段：

| 段 | 原来在哪 | 谁写 |
| --- | --- | --- |
| `dispatches` | `dispatches.json` | **两个写者，两个进程**：看板的派工路径 + 值班路径 |
| `acks` | `acks.json` | 看板 |
| `dismissed` | `dismissed.json` | 看板 |
| `bossSession` | `boss-session.json` | 看板 |

收口之后：**一个文件、一把锁、一条写路径**。派工账那两个写者不再各写各的——它们写的是同一段，
锁的是同一把锁（`json-ledger.mjs` 的目录锁，跨进程有效）。

### 一次性迁移，不做双读

老文件在 store 文件还不存在时**读一次**，读进来的就是 store 的内容；之后老文件**再也不被读**
（它们留在盘上，是用户的数据，不删，但只是历史快照）。

**不做「新旧双读」**：新旧两套都读，就是两份口径，而这个仓库已经因为多处口径不一致吃过亏
（主规格 §25.1：判据必须只有一个）。要么老文件是历史，要么老文件是真相，不能两者都是。

迁移在锁里做，而且**在锁里再查一次** store 是不是已经被别的进程建好了：两个进程同时第一次
访问时，只有一个真的迁移，另一个看到 store 已经在了就直接用——不然第二个会用老文件的内容
盖掉第一个刚写进去的。

**老文件坏了要报错**，不当成「没有记录」。迁移失败就**不留 store 文件**：留下一份空 store
会让下一轮以为「本来就没有记录」，然后把同一条指令重投一次。

### 哪些状态不收进 store，以及为什么

这是这份决策里最要紧的一半——**收口不是「全部塞进一个文件」**。

1. **结论账家族（`patrol.json` / `patrol-answered.json` / `patrol-archive.json`）与
   `patrol-config.json`：不收。** 它们被大哥**按文件名直接读写**——值班技能里写着「你在收件箱里
   替大老板选一个答案（写进 `patrol-answered.json`）」，那是**手写文件**；而 CLI 至今没有
   能替代手写的 `answer` 命令。在大哥还在手写账的时候把账搬走，等于让板面读不到大哥写的东西
   ——那不是收口，那是**制造两份口径**。要收它们，得先给 CLI 加 `answer` 命令、再改大哥的两份
   文本（`~/.minimax/agents/boss/`），那是**动大哥的手**，得独立立项。
2. **看门狗自己的状态（`watchdog-state.json` / `watchdog-notices.json`）：不收。** 看门狗是
   **独立进程**（Windows 计划任务），不在 Mini App 的生命周期里。跨进程共享一个 store 会把
   两边的锁搅在一起，而它们各自的状态只有一个写者——收口换不到任何东西，只换来耦合。
3. **大哥的长期配置（`duty-intent.json` / `managed-projects.json` / `skill-library.json` /
   `thread-subscriptions.json`）：不收。** 各自由 CLI 或大哥独占写入，生命周期是「大哥的长期
   配置」，跟板面的运行时状态不是一回事。

判据是**生命周期与写者集合**，不是「文件多不多」：**同一个写路径、必须一起动的状态**收口；
**不同生命周期、不同写者**的各归各。

## 曾考虑的替代方案

**把全部十几个状态文件都收进一个 store。** 一次性做完，听起来最彻底。输在**大哥的手**：
结论账家族是大哥手写的，搬走它而不同步改大哥的契约，就会出现「大哥写的那份」和「板面读的那份」
两份账——比收口之前更糟。而且看门狗是独立进程，共享一个 store 只是把耦合换了个方向。

**用 `node:sqlite` 建一个插件状态库。** 事务能力更强。输在主规格 §2 的硬约束：运行时已经是
唯一数据源，插件不自建状态库。状态只写在 `context.dataDir` 里。

**新旧双读：store 优先，老文件兜底。** 过渡期最平滑。输在**两份口径**：过渡期一长，老文件就会
被当成真相，而它其实是迁移时的快照——于是「板上说 X、账里说 Y」变成常态，而这类不一致最难查。

**不动它，把结论写进规格就算收口。** 零风险。输在**它没解决任何东西**：G-08 要的是「跨文件一致性
问题只剩一处」，写进规格不会让派工账的两个写者合成一条。

## 后果

**换来的**：

- 派工账的**两个写者、两个进程**合成了一条写路径、一把锁。并发写毁记录的那类事故，
  在这个文件上不再有落点。
- 老文件在迁移之后**没有任何代码路径会读**——「数据在哪」只有一个答案。
- 老文件坏了会**报错**而不是被当成空账——这正是当初丢记录的那个洞。

**付掉的**：

- **板面自己的状态现在集中在一个文件上**：一次写坏，整个 store 都读不出来。这是收口本身的代价，
  换来的是「跨文件不一致」变成「单文件损坏」——后者更容易发现，也更容易修。
- **结论账家族没有收口**，G-08 因此只落地了一半。剩下的那一半要动大哥的手，得独立立项。
- 老文件留在盘上不再被读。**它们是历史快照，不是真相**——谁按文件名去读它们，读到的是迁移
  那一刻的旧数据。`patrol-cli paths` 现在会把 store 的路径一起报出来。

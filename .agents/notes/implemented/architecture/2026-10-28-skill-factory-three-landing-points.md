# Agent Note: 技能工厂要改三个落点，别只改一处

Status: implemented

## 问题

大哥的第四项职责是**技能库**：从执行中提炼技能 → 协调项目负责人调 `skill-creator` 封装 → 注册 → 派工时匹配调度 → 定期校验退役。

这条链**跨了三个地方**：

| 层 | 在哪 | 管什么 |
| --- | --- | --- |
| 知识/流程层 | 大哥私有技能 `mimic-tear-skill-forge/SKILL.md` | 完整流程：从执行中提炼什么、怎么封装 |
| 入口/路由层 | 大哥私有技能 `mimic-tear-boss/SKILL.md`（第十三节 + 派工决策树分支）+ 大哥的 `agent.md`（Own / How you work 第 8 条） | 什么时候触发、派工时怎么用 |
| 数据/工具层 | 仓库 `miniapps/mimic-tear/miniapp/node/skill-library.mjs`（注册表存储）+ `skill-cli.mjs`（CLI）+ 板面接口 `GET /api/skill-library` | 技能存哪、状态怎么算、怎么匹配 |

前两层在**大哥的 agent 目录**里（`agents/boss/...`），第三层在**这个仓库**里。

问题就在这个分裂上：**三层里任何一层的改动，单独做都是无效的，而且失效方式是静默的。**

- 只改流程层：大哥知道该怎么做，但注册表里没有那条技能，板面看不到，派工时匹配不到。
- 只改入口层：触发条件改了，但注册表没有对应条目，`match` 匹配不到，等于白触发。
- 只改数据层：注册表里有条目了，但大哥的流程和决策树不知道该怎么用，条目永远停留在 `candidate`，不会被派出去。

`skill-library.mjs` 的四态模型把这件事写死了：

```
candidate → active → stale / retired
```

`candidate` 是「识别到了但还没封装」，`active` 是「可以派工」，`stale` 是「文件没了或改名了」，`retired` 是「试过不合适」。

**而 `match` 只返回 `active`**（`skill-library.mjs` 里那句 `if (entry.status !== 'active') continue;`）。所以一条停在 `candidate` 的技能——不管它的流程写得多好——**在派工时就是不存在的**。

## 决策

### 改技能工厂的机制，三个落点一起改

任何触及技能工厂**机制**（不是单个技能条目）的改动，必须同时落在三层：

1. **流程层** —— `agents/boss/skills/mimic-tear-skill-forge/SKILL.md`；
2. **入口层** —— `agents/boss/skills/mimic-tear-boss/SKILL.md`（第十三节 + 派工决策树分支）和 `agents/boss/agent.md`（Own / How you work 第 8 条）；
3. **数据/工具层** —— 本仓库的 `skill-library.mjs` + `skill-cli.mjs` + `GET /api/skill-library`。

**只改一处就不要开始改。** 这是判断的起点，不是完成后的检查项。

### 校验退役是定期动作，不是收尾

`skill-cli.mjs validate` 检查每条注册技能还在不在盘上，并把失效的降级：`active` 且文件不在 → `stale`；`stale` 且文件回来了 → `active`。

但 `retired` **不会自动回来**——「一个 retired 条目即使文件回来了也仍然是 retired」（`skill-library.mjs` 的注释写明）。复活它是一次**刻意的动作**（显式 `status: 'active'`），不是校验的副产品。

这条规则是有意的：自动复活会让「试过不合适」的技能悄悄回到派工池里，而没人记得它当初为什么被判定不合适。

### 注册表的数据在板面目录里

注册表文件：`~/.minimax/v2/plugin-data/liveboards/mimic-tear/skill-library.json`（与 `patrol.json` 同目录）。

CLI：

```sh
node "<仓库>/miniapps/mimic-tear/miniapp/node/skill-cli.mjs" <paths|list|add|match|validate|use|retire|remove>
```

**工作区副本与发布副本同源**——仓库里那份是源，`~/.minimax/plugins/mimic-tear/` 里那份是运行时副本，改完要同步。

### 能力库视图读的是另一份数据

板面的「能力库」页面读的是 `GET /api/skills`——那是**本机已安装的 skill** 按领域分组（`miniapp/node/domains.json` 定义领域），用来判断「这个活该派给谁」。

`GET /api/skill-library` 读的是**技能工厂的注册表**——大哥提炼并封装过的那批。

两个接口、两份数据，**不要混**。前者是「本机有什么」，后者是「团队沉淀了什么」。

## 曾考虑的替代方案

**把三层合并到一处，让大哥的技能从本仓库读流程。** 合并之后只有一处要改，失效模式消失。放弃的理由：大哥的流程是**大哥的**职责，它随大哥的 agent 目录走、不随插件发版走；把它塞进插件，等于让插件替大哥决定怎么干活。放弃的代价就是现在这样——**改一处要记着改三处**，靠 note 和流程纪律兜住。

**只在本仓库落数据层，流程与入口靠大哥自己同步。** 少两个落点。放弃的理由：大哥的技能文件是**它自己维护**的，它不读本仓库的 note（也没有理由读）。指望它「记得同步」就是把一条确定的流程变成一次记忆竞赛。

**让 `match` 也返回 `candidate` 和 `stale`，靠打分排序。** 信息量更大。放弃的理由：`candidate` 的技能**还没有文件**，派出去就是派一个不存在的东西；`stale` 的技能文件已经不在了，同理。这不是排序问题，是**可用性**问题——`match` 的语义是「这个活能派给谁」，不是「注册表里有什么」。

**让 `validate` 自动复活 `stale` 条目。** 更省事。放弃的理由：「当初为什么被判定不合适」这个信息会随自动复活丢失，而那恰恰是退役记录的价值。放弃的代价：文件回来之后要手工 `use`/`add` 一次。

**把四态简化成三态（去掉 `retired`）。** 少一个态要维护。放弃的理由：`retired` 和 `stale` 是**完全不同的两件事**——`stale` 是「文件没了」，`retired` 是「试过，不合适」。合并它们就丢掉了「不合适」这个判断，而那正是退役机制存在的理由。

## 后果

**换来的**：技能工厂的改动有了确定的落点清单，不用靠记忆。`match` 只返回 `active` 这条语义保证了「派工池里只有能用的」。

**付掉的**：

- **改机制的成本是三处。** 这是分层换来的隔离成本的直接代价——分层让每一层可以独立演进，代价是跨层变更要同步。
- **前两个落点不在这个仓库里**，所以**改完在本仓库跑测试验证不了整条链**。能验证的只有数据层和板面接口。
- **「只改一处就不要开始改」是纪律，不是机制**。没有守卫脚本能检查「这次改动是否该同时改另外两处」——那需要跨仓库的意图推断。

**不做的事**：不把大哥的流程搬进本仓库；不合并四态；不让 `match` 返回不可用的条目。

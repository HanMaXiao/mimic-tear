# Agent Note: 直通的唤醒收敛 —— 在途合并，事件不丢

Status: implemented

## 问题

方案 A 落地后，「平行负责会话」的成本显出来了：**每 49 分钟被唤起 4 次**，每次都是一整轮
agent 回合——也就是每轮都面向大老板产出一份汇报（2026-11-01 15:09 实测：本会话收到的直通
注入是 06:21:42、06:50:37、07:01:23、07:09:23）。

根因是**事件源太密**：`project-activity` 的来源是**项目里的桌面会话活动**——桌面会话每干一次活
（提交、跑一次验收、查一次读数），那条线的负责会话就被唤起一轮。平行会话挂在另一个项目上，
**不自激**；但兄弟会话每在项目目录里干一次活就会再唤一次。

连带的第二个问题：**「已投出」在板面上滞后一轮回合时长**（实测 11 分钟）——`delivered` 是投递
成功之后才落盘的，而成功信号要等负责会话那一轮结束才回来。那段时间里盯盘只看得见「已投出 =
旧的」，很容易误读成「没投出去」（2026-11-01 15:09 实测：盯盘自己差点这么读）。

## 决策

**在途（in-flight）是独立的第三个状态**（在途 / 已投出 / 没投过），各管各的；**命中在途就把
新活动并进来，事件不丢，唤醒次数降下来**。

1. **投递发出即写在途标记**，不等回合结束（已落地：`08ae155`）。
2. **判定「正在处理同类事件」读在途，不读 `delivered`**：`delivered` 的窗口永远是空的
   （要等回合结束才落盘），拿它判就是**合并逻辑一行都命中不了**。
3. **认领**（`ThreadSubscriptions.claimDelivery`）：一次读-改-写，在**跨进程锁**里。没有在途
   → 这一笔归我发；有同类的在途 → **并进来，本轮不投**（事件不丢，等那一轮结束后按**合并后
   的最新活动时间**再投一次）。
4. **尾巴投递**：在途期间并进来的活动，**那一轮结束后按最新值再投一次**——一串连续活动因此
   只多唤一次，而不是每条活动各唤一次；负责会话拿到的是**最新**的活动时点，不是一串历史。
5. **过期口径**（`IN_FLIGHT_EXPIRY_MS`，默认 60 分钟）：负责会话那一轮永远不结束（卡住、被
   中断而没 resolve）时，旧标记作废、照常投递——**不让一个卡死的会话把一条线永久合并掉**。
   过期那条里并进来却从没投出去的事件会被补投，不丢。
6. **单飞闸退役**（删掉 `single-flight.mjs`）：那是钝器——一条线的长投递挡住**所有**线；在途
   标记是精确的（按项目 + 事件类型），**别的线照常投递**。

## 曾考虑的替代方案

**把这条线的直通关掉**（`thread remove`）。放弃的理由：它会把刚被大老板拍板的能力整个撤掉，
而且别的线将来要用同一套机制——问题在**事件源与投递节奏**，不在「这条线该不该有投递口」。
（实际处置：Mimic Tear 这条线确实关掉了——理由是它的负责会话本来就是我自己的桌面端会话，
方案 A 在这条线上造的是**我的平行副本**，事件源又是我的活动（自环），且大哥本来就在管辖这条
线。**机制留着，给「负责人是另一个 agent」的线用。**）

**给平行会话换只读 agent**（`explore`）。放弃的理由：它是**权宜之计**——负责 agent 就该能干活；
它能止住「平行会话改仓库」这个风险，但止不住「每轮都产出一份汇报」这个成本。

**只把阈值调低/调高，不做合并**。放弃的理由：阈值治不了「49 分钟 4 次」——那是事件密度问题，
不是判定灵敏度问题。

**用 `delivered` 判在途**（省一个状态）。放弃的理由：**判不到**——`delivered` 要等回合结束才落盘，
那个窗口永远是空的，合并逻辑一行都命中不了。这条是 2026-11-01 15:09 那个平行会话查出来的。

## 后果

- **唤醒次数降下来**：一串连续活动 → **2 次唤醒**（第一发 + 合并后的那一发），而不是每串一次。
- **中间状态被折叠**：负责会话只看到最新活动时点，看不到中间那几次。**这是要的效果**（它要的
  是「现在怎么样」，不是「这几分钟里发生了什么」），但要让负责人知道中间状态没了。
- **在途标记可能悬挂**：负责会话那一轮永远不结束 → 标记一直挂着 → 那条线的投递一直被合并
  → 事件一直不投。所以有**过期口径**（默认 60 分钟）；过期之后照常投递，最多多唤醒一次。
- **跨进程的窄窗口**：认领是「一次读-改-写 + 跨进程锁」，所以两个 tick 不会同时认领同一笔；
  但两个**进程**同时读到「没有在途」的那个瞬间仍在（锁把窗口收窄到一次写，不消除）。
  同进程内没有这个窗口（认领是顺序的）。
- **尾投递多一次写**：在途合并的记账要读一次当前在途记录（并进来的事件是在途期间才写进去的）。

## 验证

- **测试**（`tests/direct-delivery-coalescing.test.mjs`，+6，走**真实模块**：
  `ManagedProjects` / `PatrolStore` / `ThreadSubscriptions` / `deliverToThreads` /
  `makeTrigger` / `renderDelivery`，只注入宿主边界上的 `agent`）：
  ① **未命中** → 没有在途就正常投递，投完转成已投出、在途撤掉；
  ② **命中在途** → 同类事件并进来，本轮不投（事件留在在途记录里，不记账）；
  ③ **尾巴投递** → 连续 3 次活动、间隔小于一轮回合时长 → 只被唤醒 **2 次**，最终拿到的是
  **最新**活动时点（中间那次被折叠），三条事件都记账，在途不悬挂；
  ④ **在途过期** → 旧标记作废、照常投递（过期口径是为了不让卡死的会话把一条线永久合并掉）；
  ⑤ **投递失败** → 在途撤掉、事件不记账，下一轮还能被计划到，重试成功才记账；
  ⑥ **别的线不被拖累** → 一条线在途时，另一条线照常投递。
- **变异验证 5 组**（每组先证明会红再还原）：命中不并入 / 不做尾巴投递 / 过期口径失效 /
  有结果后不撤在途 / 尾巴取第一条而不是最新。
  其中第 5 组**一开始没红**——原来的用例只并进一条事件，「取最新的那条」与「取第一条」是同一条，
  测不出差别；补成「连续 3 次活动」后才变红。
- **顺带修一个 Windows 上的真 bug**：订阅表的写盘没走仓库自己的纪律（`json-ledger.mjs`），
  `rename` 遇到「文件正被扫描器占住」会 EPERM → 一次写失败。改用 `writeJsonAtomic`
  （唯一临时名 + 原子替换 + **rename 重试**）与 `updateJsonArray`（跨进程锁）。

# Agent Note: 大哥值班的触发链与三个开关

Status: implemented

## 问题

大哥（`agentName = boss`）不是一个自己会醒的程序。它的值班、巡检、发消息，全部由**本机运行时**驱动：一条 cron 定义 + 一个目标会话 + 一份板面状态文件。

这套机制散在三处，任何一处单独看都不完整：

- 规格 `docs/specs/2026-10-20-mimic-tear-design.md` 的 §15（值班：后台自治）、§20（停工指令必须落到 cron 提示词）、§21（管辖范围与授权真实性）、§22（管辖权：可授予的状态）、§27（值班意图文件）记的是**原则**；
- 运行时库里的一行 cron 定义 + 一行调度器状态记的是**当前的触发权**；
- 大哥自己维护的一份规则文件记的是**它实际遵守的条款**。

结果是：**任何一个只读其中一处的人，都会得出错误结论**。

实际踩过的坑：

- 2026-10-27，大哥把大老板 12:59 的公开范围问卷当成 pending，**自行答了 keep**（13:10:40）——而大老板本人 13:08:05 已经答过。它能代答，是因为它有代答的机制（`patrol-answered.json` 逐条记录）。
- 停工指令只发了一条消息就以为生效了——但 cron 每 30 分钟重跑一次，prompt 里写着「恢复异常中断的活」，下一轮就把活派回去了。规格 §20 记的就是这个：**停工必须写进会被周期性重读的那个地方**。
- `patrol-config.json` 的 `enabled` 是 false、`duty-intent.json` 是 `resting`，但**这不等于它不会醒**——触发权在调度器那一侧，不在板面这一侧。

另外还有一层：这个仓库是**公开的**（`github.com/HanMaXiao/mimic-tear`）。大哥的规则文件、cron ID、运行时库路径都在仓库外面，不在这个仓库里。所以下一个 agent clone 仓库时，对这套机制**一无所知**。

## 决策

### 规格记原则，这份 note 记「今天长什么样」

规格 §20/§21/§22/§27 已经把原则写死了，**这里不复述**。这份 note 补的是规格补不了、也只有实测才知道的那一层：**机制的实际接线、开关的位置、证据在哪查**。

原则与现状的分工：规格说「触发权归大老板」「停工要落到 cron 提示词」「管辖权是可授予的状态」；这份 note 说「触发权具体是哪个 cron 定义、调度器状态在哪张表、开关是哪三条命令、证据在哪个文件」。

### 触发链：cron → 会话 → 板面

大哥不是自己醒的。触发链是：

```
cron 定义（运行时库）→ 调度器（运行时库）→ 目标会话（大哥自己的）→ 板面状态文件
```

四个环节各自独立，**任一环节的状态都能单独掐死整条链**。要判断「大哥现在会不会动」，必须同时看四处，不能只看其中一处。

### 三层触发规则

被叫醒和主动是两回事。规则分三层：

1. **没被叫醒** → 不自行巡检、不主动给负责人会话发消息、不上板新增结论。
2. **被叫醒，但大老板这轮没给具体差事** → 醒着待命。不取事实、不巡检、不发消息、不上板、**也不交班**——那轮不算值班，不刷值班戳。
3. **被叫醒，且领了差事** → 照常取事实、干活、汇报、交班，但**只做被要求的那件事，不顺手巡检**。

第 2 层是最容易写错的一层。「大哥醒了」不等于「大哥开始干活」。值班意图切到 `resting` 时也是同一个道理：**休息不是故障**——看门狗的 `alertable = stale && mode !== 'resting'` 因此不报掉线，板面值班灯也认 resting，显示「大哥休息中 · 召唤才醒」。

### 投递走 session send，不走板面派工通道

大哥给项目负责人投递，用的是原生 `mavis` 工具的 `session send`，直接打到「项目负责人根会话」——也就是干那个项目的会话。

**它不走板面的派工通道**：板面的 `dispatches.json` 不更新。区分这两种投递很重要，因为只有一条路会进派工账。

投递链路的硬限制（规格 §3.5 已记）：负责人用 `ask_user` 会**阻塞会话**，运行时只有会话主人能解开——实测 `session send` 只排队、`force_steer` 被拒、`agent.answer` 报 `session_not_found`。所以大哥要给负责人发常驻授权，让对方别阻塞。

### 规则改文件，不碰线上

大哥自己的条款在 `agents/boss/state/cron-prompt-duty-canonical.txt`（它自己维护）。铁律是：**「改规则只改文件、不碰线上」**——线上 cron 的 prompt 是薄壳，第一句就是「先完整读这个权威文件」。

这条把「改行为」和「改线上」解耦了：改权威文件 → 下次 cron 读到 → 行为变了；线上 prompt 保持薄壳，不做二次同步，因此不会出现「文件改了、线上还是旧的」。

反过来也成立：**停工指令必须落到 cron 的 prompt 上**，只发一条 session 消息是不够的。

### 三个开关

停大哥有三条路，按影响从大到小：

| # | 动作 | 命令 / 位置 | 效果 |
| --- | --- | --- | --- |
| ① | 摘掉管辖 | `node patrol-cli.mjs manage remove "<项目>" "<大老板原话>"` | 名单空了它什么都不管——**那不是失职** |
| ② | 停掉那条 cron | 运行时库 `local_runtime_v2_cron_definitions` / `local_runtime_v2_scheduler_jobs` | 触发权收回，它不再被叫醒 |
| ③ | 改它的规则文件 | `agents/boss/state/cron-prompt-duty-canonical.txt` | 约束它只上报、不代答 |

选①还是②还是③，取决于**想让哪一段失效**：① 只摘一个项目的管辖，② 整体不再触发，③ 保持触发但改行为。**要「彻底停手」通常得组合**：比如大哥已经代答过卡，光摘管辖不管用，得同时约束它不再代答。

### 证据在哪查

**运行时库** `~/.minimax/v2/sqlite/runtime-state.sqlite`（只读）：

| 表 | 查什么 |
| --- | --- |
| `local_runtime_v2_cron_definitions` | cron 的 prompt、修订号、是否已删除（`deleted_at_ms`） |
| `local_runtime_v2_scheduler_jobs` | **enabled 的真相**在这里的 `state` 字段，不在 cron 定义里 |
| `questionnaire_requests` | 卡片状态、**是谁答的** |
| `local_runtime_message_rows` | 跨会话投递，`source=communication / role=user` 的行是大哥发来的 |

**板面状态** `~/.minimax/v2/plugin-data/liveboards/mimic-tear/`：`patrol-config.json`（`enabled`、`lastRunAt`、`dutyIntervalMinutes`）、`duty-intent.json`（`mode`、`requestedBy`）、`duty-heartbeat.json`、`patrol-answered.json`、`dismissed.json`、`boss-session.json`、`managed-projects.json`、`skill-library.json`。

## 2026-11-01 的实测状态

**这一节是快照，不是常态。** 下面每一条都会过期——**用之前先按上面的「证据在哪查」重新读一遍**。

| 事实 | 2026-11-01 的读数 |
| --- | --- |
| 当前 cron 定义 | `2a1d79e8-7d5b-4b2d-9387-006ad758785c`「大哥值班巡检」，agent=boss，rev=4 |
| 上一代 cron | `672fde94`，2026-10-22 已删除 |
| 调度器 `16070206-5647-4579-9d88-f0bc34dc2a42` | `state` = **`cancelled`**，`next_run_at_ms` = null |
| 最后一次执行 | 2026-10-27T05:07Z |
| `duty-intent.json` | `mode: "resting"`，`requestedBy: 大老板 2026-10-27 13:19` |
| `patrol-config.json` | `enabled: false` |

**读法**：cron 定义的 `deleted_at_ms` 是 null（它本身没被删），但**调度器把它停了**（`state = cancelled`）。所以结论是「当前不触发」。

但这个结论**不来自板面**——`duty-intent.json` 的 resting 和 `patrol-config.json` 的 `enabled: false` 都不能证明它不会醒。**能证明的是调度器那一行**。

## 曾考虑的替代方案

**把触发链的具体接线也写进规格。** 规格 §15/§20/§21/§22 已经承载了原则，规格里再塞 cron ID、调度器 ID、表名，会让它同时承担「产品定义」和「运行时接线快照」两个角色——而后者每周都在变。放弃的代价：**要查接线得跳到这份 note**。

**只写一份「大哥操作手册」放在 `docs/`，不进 note 树。** `docs/plans/` 和 `docs/specs/` 都在 `docs/` 下，习惯上会往那儿放。放弃的理由是**时效性**：这是一份带实测读数的快照，按 `docs/` 的惯例会被当成「当前事实」原地修订，读的人会以为它没过期。而 note 的「kept current」规则要求**快照带时点**。

**把「三个开关」做成可执行命令（`patrol-cli manage stop` 之类）。** 一条命令停掉整条链，比查表改表稳。放弃的理由是这属于**大哥 agent 的职责范围**，不在本仓库——大哥的 CLI 在它自己的 agent 目录里，不在 `miniapps/mimic-tear/miniapp/node/`。要加这个能力，得改大哥的技能文件和入口路由（那是另一个仓库的事）。

**只记「停工指令必须落到 cron 提示词」这一条**（规格 §20 已记）。不够——同一个坑还有另外两个变体：管辖没摘（授权链对不上）、规则改在别处（大哥读不到）。三条一起记，才是一套完整的停手方式。

**在 note 里写下完整的 cron ID 和调度器 ID 当常量。** 放弃。ID 会变（上一代 `672fde94` 就是 10-22 换掉的），写死必然过期。折中：**正文不依赖具体 ID**，ID 只出现在带日期的实测快照里，且明确标了「用之前重查」。

## 后果

**换来的**：停大哥这件事从「知道有个人会自己动、但不知道动的是谁、怎么让它停」变成「三条开关、每个开关的作用范围、证据在哪查」。代答卡这类越权行为有了明确的发现位置（`patrol-answered.json`）和堵法（开关③）。

**付掉的**：

- **这份 note 会过期。** 实测快照那节尤其快。靠标注「快照、用前重查」降低误导，但不消除。
- **运行时库路径和表名是内部约定**，换一个 MiniMax Code 版本可能就变。表名以 `runtime-internals` 主题记忆里的实测为准，结构变了要回来改这份 note。
- **三个开关的边界不是互斥的**。「彻底停手」通常要组合 ①②③，note 里列了表但没写组合策略——那是操作现场的事。

**不做的事**：不代替大老板改管辖或停 cron；不动大哥的规则文件；不把触发链接线写进规格。

# Agent Note: 守卫脚本用零依赖 Node 实现，守测试盖不到的缺口

Status: implemented

## 问题

这个仓库从一开始就有一条硬约束：**包内不得出现 `node_modules`，不得声明任何第三方依赖**。`scripts/check-package.mjs` 把这条写成了可执行断言（包内无 `node_modules`、无 lockfile、`package.json` 无 `dependencies`、import 说明符只有 `node:` 内置模块与相对路径、源码里没有烤进构建机的绝对路径）。

原因不是洁癖：Mini App 的运行时是**裸 Node 环境**，宿主加载 Mini App 时没有安装步骤。包里只要出现一个第三方 import，宿主加载时直接炸——而这个炸法是在**用户装上插件之后**才发生的，不是在开发者跑测试的时候。

约束一旦这么硬，工具链的选择就窄了：

- 装不了 ESLint / Prettier / Biome（要依赖），
- 装不了 Vitest / Jest（要依赖），
- TypeScript 编译器本身也是依赖（仓库里只有一个 `miniapp/node/miniapp-api.ts`，是宿主提供的声明样例，谁也不 import 它）。

于是 2026-10-28 那一轮（提交 `c8a5cce`）加 CI 门禁时，只有两个选择：写零依赖的 Node 脚本，或者放弃门禁。

而门禁本身要守的东西，恰恰是**测试盖不到**的：

- **发布漂移**：看门狗跑的是已发布副本（`~/.minimax/plugins/mimic-tear`），不是仓库工作区。「改的是源码、跑的是旧代码」不会让任何测试变红，只会让线上行为和代码对不上。测试跑的是工作区，永远发现不了工作区和发布副本不一致。
- **包内依赖与路径泄漏**：测试在有 `node_modules` 的开发机上跑，永远看不见「包多带了一个依赖」。
- **风格**：运行时里的 `console.log`（应该走 `context.logger`）、源码里遗留的 `TODO`/`FIXME`、客户端里的 emoji。

这三样都是「环境本身就是被检查的对象」的检查。测试跑在被检查的环境**之内**，天然看不见。

## 决策

### 守卫是独立脚本，不是测试

`scripts/` 下每个守卫是一个**能单独跑的 `.mjs`**，退出码统一：

| 退出码 | 含义 |
| --- | --- |
| 0 | 通过 |
| 1 | 发现违规 |
| 2 | 用法错误（目录不存在、参数不对） |

CI 里每一步独立，失败即标红。守卫脚本自己也被测试覆盖（`tests/packaging.test.mjs` 跑全部四个脚本），所以「守卫本身坏了」也会被发现。

### 守卫只守这个仓库真在守的规矩

不做通用 lint。`check-style.mjs` 只管三条：运行时里不许有 `console.log`/`console.error`、源码里不许留 `TODO`/`FIXME`、客户端里不许有 emoji。第三条的检测正则**运行时从 `tests/client-contract.test.mjs` 现读**，不是抄一份——抄两份就等于两份都能漂移。

守卫的定位是「**把最容易被绕过的几条约定钉成断言**」，不是「把所有风格问题都抓一遍」。抓不全没关系，抓准了才有用。

### 路径不进脚本

守卫的根目录通过环境变量传（`MIMIC_TEAR_REPO_ROOT`、`MIMIC_TEAR_PACKAGE_DIR`、`MIMIC_TEAR_PUBLISHED_DIR`），默认值是「脚本所在仓库的根」和「用户主目录下的插件目录」。脚本里不写死本机绝对路径——这既是 `check-package.mjs` 第 5 条断言的要求（否则守卫自己就把路径泄漏进包了），也让同一份脚本能在 CI runner 上跑。

### 检查要能看出「没生效」

`check-published.mjs` 的比对是逐文件 `Buffer.equals`，并且**两个方向的差集都列出来**：「仅在仓库」= 新增文件没进发布包，「仅在发布副本」= 副本里有仓库没有的文件，说明它是被旧发布流程留下的。

存在性检查不算比对——它只回答「文件在不在」，不回答「内容一不一样」。一个改了一半的副本，文件都在，但跑的是旧逻辑。

默认**不算**仅行尾差异（CRLF/LF 归一化后代码完全一样，跑起来的行为没有区别）；要严格按字节比就设 `MIMIC_TEAR_STRICT_BYTES=1` 或传 `--strict-bytes`。

### 仓库没有插件时，CI 仍然要绿

CI runner 上没装插件，`check-published.mjs` 打印 `SKIPPED` 并以 0 退出。这不是「检查没做就算了」——是这个检查**在那个环境里不适用**，硬红只会让人学会忽略红。

### 提交纪律是第五个守卫，但是本地的

`scripts/install-hooks.mjs` 装一个 `pre-commit` 钩子，管两条：声明了提交范围（`MIMIC_TEAR_COMMIT_SCOPE` 或 `<git-dir>/mimic-tear-commit-scope.txt`）时，暂存区里有范围外的文件就拒绝；暂存的文件在**同一仓库的另一个工作树里**也是脏的，就拒绝——那是别人的在制品。

它**默认不装、也不在 CI 里**（新 clone 的仓库没有钩子，得手动 `node scripts/install-hooks.mjs`）。而且它**故意 fail-open**：钩子坏了不拦提交。理由是提交纪律的真正目标是**别把别人的在制品卷进 commit**，而这条在 CI 上根本查不了（CI 只有一个工作树）。它只能作为本机的一道提醒，不能当保证。

### 2026-11-01：note 门禁加入同一族

`.agents/notes/` 的结构与格式门禁 [`scripts/verify-agent-notes.mjs`](../../../scripts/verify-agent-notes.mjs) 按同样的形态写：纯 Node 内置模块、独立可跑、退出码 0/1/2、路径靠环境变量传、CI 里单独一步。

它守的缺口和前三个一样——**测试不会因为「有人写了份格式不对的 note」而变红**。

## 曾考虑的替代方案

**用 ESLint / Prettier / Biome 做风格检查。** 成熟、覆盖面广、配置生态好。但它要依赖，而依赖会让包装不上（`check-package.mjs` 的第 1、3、4 条断言会直接红）。而且通用 lint 报告的是**通用问题**，不是这个仓库特有的那三条约定——真正要守的是「运行时走 `context.logger`」和「客户端不许有 emoji」，这两条通用 lint 都不知道。放弃的代价：通用问题（缩进、引号、分号）一律不管——反正这个仓库本来就不靠格式门禁活着。

**把这些断言写成 `node:test` 的测试，放进 `node --test`。** 更省事：不用新脚本、不用改 CI。放弃的理由有两个。一是**可执行性**：`node --test` 失败时的报错是一坨 TAP，而守卫脚本的输出是给人看的中文清单（`miniapp/node/foo.mjs:12:5 用了 console.log，运行时请走 context.logger 的结构化日志`）。二是**退出码语义**：守卫要有 0/1/2 三态，测试只有 0/1，而且测试失败时「是断言没满足」和「脚本自己报错了」混在一起分不开。

**把守卫装成 `npm scripts`，用 `pnpm run guard` 统一调。** 仓库**根本没有根 `package.json`**（`miniapps/mimic-tear/package.json` 只是个 mcode 指针），引入 package.json 就得引入 lockfile 约定，`check-package.mjs` 的第 2 条断言（包内无 lockfile）虽然只扫包目录，但仓库根多一套工具链约定是另一回事。放弃的代价：CI 里要写四五行完整命令，没有 `pnpm run guard` 短。

**发布漂移检查放进 `node --test`。** 看起来更统一。放弃的理由是**它不是测试**：`check-published.mjs` 断言的是「两个目录一致」这个**环境事实**，不是「代码行为正确」。它没有测试用例、没有断言失败信息，它的结论就是「一致 / 不一致 / 环境不适用」三态。塞进测试里，失败时你分不清是代码坏了还是发布没同步。

**守卫脚本用 TypeScript 写，编译后跑。** 类型更严。但编译工具链本身就是依赖，而且仓库里已经有一个 TS 文件（`miniapp/node/miniapp-api.ts`）明确是**样例、谁也不 import**，再加 TS 只会让人以为这仓库在用 TS。放弃的代价：守卫脚本没有类型检查，逻辑写错只能靠跑出来发现。

**提交纪律也进 CI。** CI 里跑不了「另一个工作树里有没有人在改」——CI 只有一个工作树，这个检查在 CI 上恒为通过。检查恒通过和没有检查在结果上无法区分。放弃的代价：**CI 不保证提交纪律**，这条只能靠本机钩子，而钩子默认不装。这是明确接受的缺口。

## 后果

**换来的**：三条最容易绕过的约定（零依赖、无发布漂移、无风格违规）变成了 CI 上的红灯，不是「靠大家记得」。守卫脚本自己也有测试覆盖，所以守卫坏了不会被当成「守卫通过」。

**付掉的**：

- **没有通用 lint**。缩进、引号、行宽一类的事没人管。这个仓库的风格靠代码评审维持。
- **守卫要自己维护**，没有社区和生态帮忙。`check-style.mjs` 里那条「emoji 正则要从契约测试现读」的约定，写法上是把一致性保障从「抄两份」换成了「耦合两处」——耦合有维护成本，但漂移成本是零。
- **提交纪律在 CI 上没有保证**，只在本机钩子（默认不装、故意 fail-open）上有一道提醒。
- **守卫只能守「机械可判定」的规矩**。「这个改动该不该走单一写路径」「这个 note 值不值得写」这类判断，脚本管不了。

**不做的事**：不引入 `package.json`、lockfile 或任何依赖；不引入通用 lint；不把守卫并进 `node --test`。

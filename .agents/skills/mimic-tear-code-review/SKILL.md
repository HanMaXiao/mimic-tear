# 评审这个仓库的一次改动

**评审的产物是「有证据的判断」，不是「一段感想」。** 一个有实据的阻塞项，比十条吹毛求疵有用。

## 先读要求，再看 diff

**拿记忆里的规则去对 diff，是违规漏过去的主要方式。** 动手前先打开：

| 要求在哪 | 管什么 |
| --- | --- |
| [`AGENTS.md`](../../../AGENTS.md) | 常驻约定：命令、硬约束、提交纪律 |
| [`docs/specs/2026-10-20-mimic-tear-design.md`](../../../docs/specs/2026-10-20-mimic-tear-design.md) §3 | 四层职责与写路径的硬约束 |
| 规格 §5 | API 与 SSE 契约 |
| 规格 §9 | 验收标准（**四层**：代码在 / 测试过 / 生产路径跑起来是什么样 / 新代码真的跑起来过吗） |
| [`.agents/notes/`](../../notes/README.md) | 已经定过的决策。**不同意一条 note 是设计讨论，不是自动否决** |
| [`docs/plans/2026-10-22-line-ownership.md`](../../../docs/plans/2026-10-22-line-ownership.md) §3 | 提交纪律 |

然后把改动的路径映射到这些要求上，**逐条对**，再读 diff。

## 重点查这几类

### 口径不一致

这个仓库最怕的就是「三处说法不一样」。查：

- **API 契约三处**：规格 §5、`api-routes.mjs`、客户端端点表。`tests/api-contract.test.mjs` 会对账，但它只查**存在性**，不查**载荷形状**——形状变了要人看。
- **插件技能里的接口表**：`miniapps/mimic-tear/skills/mimic-tear-board/SKILL.md` 记着路由与 SSE 事件的清单。接口改了它没改，用户手上的技能就是错的，**而测试抓不到**。
- **文档里的数字**：条数是产物不是常量。文档里写死的数字会过期。

### 写路径越界

- 所有写操作走同一条路径：`HTTP → 校验 → ProjectService → 持久化提交 → SSE 广播`。路由里直接写文件是越界。
- **先提交再广播**，广播失败不回滚。
- 运行时库 `runtime-state.sqlite` **只读**。任何以写模式打开它的代码路径都是阻塞项。
- 派工账 `dispatches.json` 有**两个进程两个写者**，都是读-改-写。改这块要特别小心（已修过一次：`tests/persistence.test.mjs` 钉着那个固定临时文件名的 bug）。

### 发布漂移

**改的是源码，跑的是旧代码**——这个仓库最常见的一类问题。

- 改的是 `miniapps/mimic-tear/` 吗？改了就要问：**发布副本同步了吗？**
- 发布副本在 `~/.minimax/plugins/mimic-tear/`。`scripts/check-published.mjs` 逐字节比对，**两个方向的差集都列**（仅在仓库 / 仅在发布副本）。
- Mini App 的 `lifecycle` 是 `on-demand`——**板面没开时 Node 服务根本没跑**，所以「文件换了但没重启」等于「没换」。

### 没被测到的地方

测试跑在被测环境**之内**，所以有些事它天生看不见：

- **发布副本与仓库不一致**（工作区永远和发布副本「一致」，测试就红了）。
- **包内多了一个依赖**（开发机上有 `node_modules`，测试照样绿）。
- **运行时里的 `console.log`**、**源码里遗留的 `TODO`/`FIXME`**、**客户端里的 emoji**——这三个由 `scripts/check-style.mjs` 守，测试不守。
- **Windows 计划任务链**、**看门狗心跳**——需要另外的验收技能，见 `miniapps/mimic-tear/skills/` 里的三个项目自用技能。

### 测试强度

- **断言要能红。** 一个断言在它该抓的回归面前不红，等于没有断言。
- **别信测试自己的报告**，信它断言的外部状态。
- **改了行为的测试要跟着改断言**，不要为了让它绿而放松断言。
- **`node --test` 不是零副作用**：它会创建/删除/恢复 Windows 计划任务 `MimicTear-DutyWatchdog`。评审时别把它当无害操作。

### 风格与打包

`scripts/check-style.mjs` 和 `scripts/check-package.mjs` 守的三条 + 五条，diff 碰到的部分要自己先看一眼——CI 会红，但**评审时就该发现**。

## 提意见的方式

- 说清**缺陷、位置、影响、证据**。
- **阻塞项和建议分开**。已经被绿门禁挡住的问题不要重复提。
- **和作者的分歧要说理由**，不要用「我觉得」代替论证。
- 收到评审意见时，**逐条核实**再改或驳回——不接受表演式的同意，也不为「礼貌」接受错的结论。

## 别做的事

- 别在评审里顺手改代码。
- 别用「实现无误」代替「未通过项如实报告为未验证」。
- 别把「看起来对」当成通过——**哪里有证据，哪里写**；没查到的写没查到。

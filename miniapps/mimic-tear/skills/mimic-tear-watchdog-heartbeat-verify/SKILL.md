# 心跳 / 看门狗验收

监控类循环最危险的失败不是「报错」，而是**看起来一切正常地什么都不做**。这个技能是一份验收清单，用来回答一个问题：**它到底还在跑吗？**

## Inputs to collect

- **它自己写的状态文件在哪**（心跳 JSON、watchdog state、日志）。问不到就去找它写的产物——监控程序几乎都会留一个自己的状态文件。
- **周期是多少**（心跳 1 分钟 / 看门狗 5 分钟 / 轮询 10 分钟）。没有周期就没法判断「没推进」。
- **它本该报给谁**（板面收件箱 / 值班会话 / 看板某页）。这决定了验收的最后一步查哪里。

## Procedure

1. **先看产物，别看进程。**
   原因：这类监控常跑在宿主进程里（Electron / 桌面应用 / 计划任务子进程），按进程名过滤往往根本查不到独立进程；反过来进程活着也可能根本没在跑。
   做法：找到它写的状态文件，读里面的时间戳/计数。

2. **读两次，比间隔。**
   原因：单点快照会误判——刚好在两次 tick 之间看一眼，看到的就是"没动"。而且两次之间的间隔要 ≥ 一个周期，短于周期可能只是它还没到点。
   做法：间隔一个完整周期读两次，比较**时间戳是否推进**、推进量是否 ≈ 周期。
   注意：连续两次间隔精确等于周期，是强证据；间隔漂移或忽快忽慢，说明它被别的负载拖住了。

3. **排除「恒判健康」。**
   原因：这是最阴的一类——逻辑写着"如果时间差超过阈值就告警"，但时间差永远是 NaN，NaN 跟任何值比较都是 false，于是**永远不告警**。
   典型来源：`Number(options.now) ?? Date.now()`。`Number(undefined)` 是 `NaN`，而 `NaN` 既不是 `null` 也不是 `undefined`，`??` 不会兜底 → 兜底失效。
   做法：找出所有时间兜底点，逐个确认「生产调用路径不传参时，兜底真的会生效」。别只读兜底那行，要顺着**生产的调用点**看它传没传。

4. **排除「钉死链」。**
   原因：监控里硬编码的 cron id、任务名、目标会话 id，会在调度器换靶、任务被删、目录被搬之后变成死链。而"没有 run 产生"和"出了事但没产生 run"在日志里长得一模一样。
   做法：把代码里引用的每个 id/名字拿去查——它还存在吗？enabled 吗？最近一次触发是什么时候？
   判断口径：**先看 job 状态 + run_count + 最后一次触发时间**三件套，再看"没有产出"。

5. **排除「测试全绿是假绿」。**
   原因：如果所有单测都**显式传了**时间/参数，而生产路径不传，测试跑的根本不是生产形状——全绿是假绿，这不是运气问题。
   做法：补一条**用生产调用形状**跑的用例（不传可选参数，直接调生产函数），看它是否还能正确判活。

6. **确认告警真的送得出去。**
   原因：监控算对了不等于告警到了人手里。告警可能只写进了自己的日志文件，而看板读的是另一个文件。
   做法：追一条完整的链路——检测到异常 → 写到哪个文件/通道 → 接收方读的是不是同一个。**特别验证「宿主应用关着」的情况**：如果链路依赖一个常驻的桌面应用，它一关，监控和告警一起消失，这几天就会静默。

7. **记下基线数字。**
   原因：下一轮要靠数字对比判断"有没有动"，光说"还在跑"没有信息量。
   做法：记录状态文件路径、当前时间戳、上一次与本次的间隔、漏报累计数。

## Output contract

一段验收结论，包含四部分：

- **状态**：健康 / 失效 / 静默（判定依据是什么，不要只给结论）
- **证据**：状态文件路径 + 两次读到的真实时间戳 + 关键代码位置（文件:行）
- **缺陷清单**：每条写清触发条件、观察到的现象、支撑证据
- **下一轮要盯的第一件事**：一句话，指明要看哪个文件的哪个字段

## Failure handling

- **状态文件读不到 / 不动**：先确认调度器有没有真的启动它（第 4 步三件套），而不是先怀疑它自己的代码。启动链问题按「先手工跑、再查调度器路径」的顺序排。
- **两次时间戳没推进但也没报错**：不要用"看起来正常"代替一次真实读取，直接报"无法确认它在跑"并说明卡在哪一步。
- **发现缺陷但拿不准是不是真缺陷**：先在目标环境复现一次再报。复现不了就写明"假设"和"未验证"，别把它算成已确认。

## Examples

**Input**：看门狗一周没报过警了，状态文件看着挺正常。

**Output**：判定**静默失效**。证据：`watchdog-state.json` 的 `checkedAt` 停在 10-26 14:36，两次读取间隔 12 分钟没有推进；心跳模块里硬编码的 cron id `672fde94…` 在 10-22 05:57 已被删除，调度器里现在活着的不是它。缺陷两条：① 钉死链——心跳读的是一条不存在的 cron，"没有 run"因此和"没事发生"无法区分；② 恒判健康的隐患——`Number(options.now) ?? Date.now()` 在生产调用不传 `now` 时得到 NaN，所有时间比较为 false。下一轮先看 `duty-heartbeat.json` 的 `brokenSince` 字段。

**这两条后来都修掉了**（验收时先确认缺陷还在不在，别照着旧结论直接报）：

- 钉死链：改成**按名字解析**目标 cron，不再硬编码 id——见 `miniapps/mimic-tear/miniapp/node/duty-chain.mjs`，节点侧只读 `patrol-config.json` 里的 `dutyCronId`，由用户钉住当前活着的那个。
- 恒判健康：兜底改成 `Number.isFinite` 判断——见 `miniapps/mimic-tear/miniapp/node/duty-heartbeat.mjs` 的 `resolveNow`，`NaN` 不会再悄悄活下来。

本项目的状态文件在插件的 dataDir 里：`watchdog-state.json`（`watchdog.mjs`）、`duty-heartbeat.json`（`duty-heartbeat.mjs`）；告警流水走 `watchdog-alerts.mjs`，板面用 `GET /api/watchdog/alerts` 读。

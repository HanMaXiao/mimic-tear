# 计划任务启动链自检

Windows 计划任务的失败大多发生在**启动链**上，不在被启动的程序里。症状高度统一：**什么都没发生，但报告显示成功**。这个技能是把启动链逐环验完的清单。

## Inputs to collect

- **任务的 XML 或 `schtasks /Query /TN "<名字>" /XML`**。
- **被启动的目标**：哪个程序、哪个脚本、它应该产出什么文件。
- **怎么判断"它跑了"**：必须有一个**它自己写的产物**（状态文件、日志行）。没有产物就没有验收依据。

## Procedure

1. **先分清"没触发"和"触发了但没跑起来"。**
   原因：这是两种完全不同的病，治法不同。看门狗式的三件套——**job 状态 / run_count（累计触发次数）/ 最后一次触发时间**。
   - 触发次数没涨 → 调度侧的问题（任务被删、调度器没在跑、触发器没到点、作业被暂停）。
   - 触发次数涨了但没产物 → 启动链的问题，往下走。
   - 两者都没涨但任务显示"上次运行 0" → 那是上次的结果，不是本次的，别混。

2. **`<Command>` 里只能放可执行文件。**
   原因：`<Command>` 是要被 `CreateProcess` 的**程序路径**。把 `//B`、引号、脚本路径、参数全塞进去，Windows 会把整串当成一个文件路径去"打开"——弹"选择打开方式"对话框、任务瞬间返回 0、什么都没跑。而任务记录会显示"上次运行成功"。
   做法：`<Command>` 只放裸可执行文件（如 `wscript.exe`、`node.exe`），所有参数（`//B`、脚本路径、工作目录）全部放 `<Arguments>`。

3. **工作目录 ≠ 启动目录。**
   原因：计划任务默认工作目录是 `C:\Windows\System32`；`//B` 下 `WScript.Shell.CurrentDirectory` 也不是启动目录。脚本里用相对路径会找不到文件，表现同样是"什么都没跑"。
   做法：脚本内部一律用**绝对路径**；不依赖当前目录。

4. **wscript 会吞掉运行时错误。**
   原因：`.vbs` 里的运行时错误不会让退出码变成非 0，任务记录里就是"成功"。想看真相，用 `cscript //B` 跑同一个脚本——错误会打到 stdout。
   做法：改之前先 `cscript //B <脚本>` 跑一遍；也说明**靠退出码传递成败的脚本，必须用 cscript 验**。

5. **判活看产物，不看退出码。**
   原因：`Last Result = 0` 在这条链上不构成任何证据。
   做法：让被启动的东西写自己的状态文件，然后看时间戳有没有在推进（推进间隔 ≈ 期望周期）。连续两次间隔 ≈ 周期 = 强证据。

6. **A/B 对照定位到哪一环坏了。**
   原因：直接手跑能跑、调度跑不了 → 问题一定在启动链（Command/工作目录/引号），不在程序逻辑里。这一步能省掉对业务代码的怀疑。
   做法：① 手工 `node <脚本> --data-dir <临时目录>` 跑，看产物是否更新；② 走调度路径（`schtasks /Run /TN "<名字>"`）跑，看产物是否更新。① 成功 ② 失败 → 锁定启动链。

7. **冒烟用临时 data-dir，别用生产目录。**
   原因：用生产目录测启动链，会用测试产生的假数据覆盖真实状态戳、告警戳、交班戳——真值被抹掉，事后无法区分"没发生"和"被覆盖了"。
   做法：所有验证性运行都指向临时目录。

8. **清掉会自我续期的自测任务。**
   原因：`Queued` + `One Time Only` 的任务会自我续期一直跑，还会持续写状态。上线前留着它，它就是第二个"看门狗"在生产上乱跑。
   做法：上线清单里显式列出要删的任务名，并确认已删除（`/Query` 查不到）。

9. **记三个基线**：状态文件路径 + 期望周期 + 启动方式（任务名 / 触发器 / 续期机制）。下一轮要靠这三个数对比"有没有动"。

## Output contract

- **结论**：起得来 / 起不来 / 静默失败（判定依据）
- **证据**：任务 XML 的关键字段（`Command`/`Arguments`/`WorkingDirectory`/`Trigger`）+ 状态文件两次真实时间戳 + 手工跑与调度跑各自的结果
- **要改的具体字段**：直接给出该改 XML 里的哪一项、改成什么
- **需要删的任务**：名字 + 是否已确认删除

## Failure handling

- **手工能跑、调度跑不了**：问题在启动链，不要去改被启动程序的逻辑。
- **改了 XML 仍然没反应**：先确认任务定义真的被更新了（`/Query /XML` 读回来比对，别信"我改过了"），再往下查。
- **改完只手工验过**：不算修好。必须走一次调度路径（`schtasks /Run`）再看产物是否推进，否则下一次调度照样静默。
- **拿不到证据**：直说"无法确认它跑起来了"，并写清卡在第几步——「看起来正常」是最贵的一种结论。

## Examples

**Input**：计划任务每 5 分钟跑一次看门狗脚本，但目标状态文件的时间戳一直不动，任务显示 Last Result = 0。

**Output**：判定**静默失败，问题在启动链**。证据：任务 XML 的 `<Command>` 是 `wscript //B "<脚本绝对路径>"`（整串塞进了 Command）→ Windows 当成一个文件路径去"打开"，弹了"选择打开方式"、任务秒退返回 0；`<Arguments>` 为空；`<WorkingDirectory>` 是 `C:\Windows\System32`，而 VBS 里用的是相对路径。手工 `node <脚本> --data-dir <临时目录>` 跑，状态文件正常更新 → 锁定在启动链，不在脚本逻辑。改法：`<Command>` 只留 `wscript.exe`，`//B "<脚本绝对路径>"` 移进 `<Arguments>`，脚本内路径全改绝对路径。另发现一个自测任务是 `Queued` + `One Time Only`，会自我续期，上线前需删除。

本项目的真实形状（`miniapps/mimic-tear/miniapp/node/install-watchdog-task.mjs`）：任务名 `MimicTear-DutyWatchdog`，`<Command>` 是裸 `wscript.exe`，`//B` 与脚本路径在 `<Arguments>`，脚本是 `run-watchdog-hidden.vbs`；它交给 `<Arguments>` 的三个绝对路径是 `node.exe`、`watchdog.mjs` 与 data-dir。

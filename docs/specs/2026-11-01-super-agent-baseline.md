## 0. 一句话

文章给的不是「更好的产品」，是**一份把「人的注意力」从执行层挪到决策层的架构账本**。

我们的大哥已经长出了这张脸的一半——双层结构（§2）、外部控制回路（§6）我们比文章描述的还细；另一半——事件驱动（§3）、全双工交互（§4.1）——**基本没长**。所以现状是：**大哥能管，但它不主动**；**它管的事你还得自己盯盘**。

文章里那句最该被抄下来的话：

> 「Session 应当是系统的实现细节，而不应是用户的认知负担。」
> ——§2

我们的板面到今天仍然是**按项目**组织的（`docs/specs/2026-10-20-mimic-tear-design.md` §6.1）。也就是说：**用户还在替系统管理 Session**。这是当前最贵的一条差距，也是本文§4 缺口的 G-01。

## 1. 外部基线的结构

### 1.1 五个模块 → 四个特征

| 文章小节 | 模块 | 支撑哪个特征 | 核心机制（一句话） |
| --- | --- | --- | --- |
| §2 | **双层架构** | 连续 + 高效 | 常驻 Router 层承接全局交互与协调，上下文隔离的 Worker 层并发执行 |
| §3 | **事件驱动** | 主动 | Trigger 两级过滤 → Thread 订阅直通 → Inline & Spill → 链式召回 → 投机执行 |
| §4 | **面向人的交互** | 高效 | 异步 ReAct Loop（`start()`/`stop()`）实现全双工；按信道匹配输出带宽 |
| §5 | **计算、状态与环境的分离** | 持久 | 存算分离（云端无状态计算 + 数据库存状态）+ 端侧轻量 daemon 接入执行环境 |
| §6 | **Watchdog** | 持久 | 主系统之外的独立 Control Loop，监控基础设施**与任务进展** |

四个基础特征（§1）：**连续 / 高效 / 主动 / 持久**。

## 2. 大哥现状对账（逐模块）

证据标签见 §6。

### 2.1 双层架构（文章 §2）——**已具备，且我们更严**

| 文章要素 | 大哥的对应物 | 证据 | 判定 |
| --- | --- | --- | --- |
| Router 常驻、跨任务汇总、充当序点与记忆 | `boss` agent + 固定 cron 会话（跨轮保持上下文） | 主规格 §15.4（`:731`-`:741`） | 已有 |
| Router 不直接执行具体任务 | 只对接项目根会话，不直接指挥团队成员 | 主规格 §15.1（`:700`-`:707`） | 已有 |
| Worker 上下文隔离、并发 | 项目根会话（`parent_session_id` 为空）+ 其子会话 | 主规格 §15.1 | 已有 |
| Worker 不直接对人说话，结论回 Router 统一回复 | 大哥用 `mavis session send` 投递到根会话，结论写 `patrol.json` 上板 | 主规格 §3.3（`:162`-`:197`）、§15.2 | **方向已对，但通道是单向的**：Worker→Router 的状态回传不存在，只有大哥→Worker 的投递 |
| Session 是实现细节，不是用户认知负担 | 板面按**项目**组织（总览页逐项目一张卡） | 主规格 §6.1（`:457`）、§4.1（`:256`） | **缺** → G-01 |
| Router 层内切分 / sharding | 不需要 | 单个大老板、量级为几十个会话 | 不做（见 §5） |

> **判定**：这一层**不是缺口所在**。文章在这一节给我们的新东西只有一个——**「Session 不该是用户的认知负担」这条产品判据**，它反过来指出了 G-01。

### 2.2 事件驱动（文章 §3）——**最大的空白**

| 文章要素 | 大哥的对应物 | 判定 |
| --- | --- | --- |
| Trigger 是一等公民（环境中的半结构化事件） | 只有 cron 定时唤醒；`facts` 是一次性事实快照 | **缺** → G-02 |
| 两级过滤：程序层 Fast Path 先筛噪音，语义层 Slow Path 再判是否行动 | 全部事实每轮一次性进模型 | **缺** → G-03 |
| Thread（同一事件流）作为路由单位 | 无 | **缺** → G-04 |
| 订阅与直通（程序把后续事件直接发给 Worker） | 无；每轮靠大哥重新取事实 | **缺** → G-04 |
| Inline & Spill（上下文当 Cache 管） | 无；facts 是全量平铺 | **缺** → G-05 |
| 链式召回（按引用图多跳展开） | 无 | **缺** → G-05 |
| 投机执行（后台提前行动） | 无 | **缺** → G-06 |

> **判定**：文章 §3 是我们与它**差距最大的一个模块**，也是「主动」这个特征全缺的原因。四条缺口（G-02 ~ G-06）都落在这一节。

#### 2.2.1 信噪比已经坏了（这一节最硬的证据）

文章 §3.1 的前提是「环境事件流呈现**高噪音、低触发率**特征，绝大多数日常消息并不需要 Agent 介入」。我们的现状不是「需要把噪音滤掉」，是**噪音已经堆到收件箱里了**：

| 事实 | 值 | 证据（2026-11-01 实测） |
| --- | --- | --- |
| 收件箱结论总数 | **100 条** | `liveboards/mimic-tear/patrol.json` |
| 大老板**从未确认**的 | **93 条**（已确认 7 条） | 同上，`acknowledged` 字段 |
| 结论来源分布 | `board` **97** 条 / `duty` **3** 条 | 同上，`source` 字段 |
| 最近一条结论的时间 | 2026-10-30 11:48 | 同上，`createdAt` |

**93 条未确认意味着什么**：不是「大老板懒得看」——按文章 A1 的说法，人能同时跟的活跃线只有 3 到 5 条，而板面一次给他 93 件事、其中没有优先级也没有收敛，他唯一理性的反应就是不看。**收件箱已经退化成第二个需要盯盘的界面**，而它本该是替人盯盘的那个。

这就是文章 §3.1 两级过滤与 §4.2 带宽纪律要解决的具体问题——在我们的规模上，**它已经是问题，不是优化项**。

### 2.3 面向人的交互（文章 §4）

| 文章要素 | 大哥的对应物 | 判定 |
| --- | --- | --- |
| 异步 ReAct Loop，全双工（`start()`/`stop()`，后台跑的同时接新指令） | 一轮 cron 巡检是**同步阻塞**的：跑完才下一轮 | **缺** → G-07 |
| 输出带宽与信道匹配（原文给的硬规矩：IM 单次回复不超过 100 词） | 板面结论自由长度；值班汇报走同一通道 | **缺**（纪律未固化）→ G-07 |
| Worker 内部推理与工具调用不外泄 | 天然满足（Worker 是别的会话，推理不落到板面） | 已有 |

### 2.4 计算、状态与环境的分离（文章 §5）——**部分成立，方向需重判**

| 文章要素 | 大哥的对应物 | 判定 |
| --- | --- | --- |
| 计算与状态分离（计算无状态、状态进数据库） | Mini App 的 Node 进程是 on-demand；大哥跑在 OS 计划任务 + 固定会话里 | **部分成立** |
| 状态集中存储 | 板面状态散在 `liveboards/mimic-tear/` 下的多个 json（`patrol-config` / `duty-intent` / `duty-heartbeat` / `patrol-answered` / `managed-projects` / `skill-library` / `dispatches` …） | **缺**（次要）→ G-08 |
| 端侧轻量 daemon（BYOM）接入远端执行环境 | 只有一台机器，执行环境就是它自己 | **不适用**（见 §5） |

> **判定**：文章 §5 的动机是「跨设备持久在线」。我们的持久性瓶颈**不是设备多**，是**宿主进程会停**（主规格 §15.2）。所以 §5 的**结论我们要重新推**，不能照抄——见 §5 的否决清单。

### 2.5 Watchdog（文章 §6）——**机制已有，判据太窄**

| 文章要素 | 大哥的对应物 | 判定 |
| --- | --- | --- |
| 主系统之外的独立控制回路 | Windows 计划任务 `MimicTear-DutyWatchdog`，一次性执行 + 自我重排 | 已有，**比文章还细**（见下） |
| 监控基础设施存活 | 心跳 `duty-heartbeat` stale 判定 + toast 通知 | 已有 |
| **监控任务本身的实质进展**（模型判断 Worker 是否在推进、方向是否偏离） | 无 | **缺** → G-09 |
| Watchdog 是可被自然语言询问的 Agent Session | 是脚本，不是 Agent | **缺**（低优先） |
| Watchdog 能在线修正主系统行为 | 能改自己的计划任务调度；**不能改大哥的提示词或触发规则** | 部分 |

> 我们在 Watchdog 这条线上做过的取舍（跟着宿主生命周期、宿主不在就禁用、交班时叫醒、探针失败必须报「活着」）记录在 [`../plans/2026-10-26-watchdog-trigger-schedule.md`](../plans/2026-10-26-watchdog-trigger-schedule.md) 与主规格 §15.8。**那部分不需要重做**——文章没比我们更懂 Windows 计划任务。

#### 2.5.1 2026-11-01 的实机读数：看门狗活着，但**它不会报警**

| 组件 | 状态 | 证据 |
| --- | --- | --- |
| Windows 计划任务 `MimicTear-DutyWatchdog` | **活着**：`Ready`，Last Run 2026-11-01 02:48:52，Next Run 02:50:03，`Last Result 0` | `schtasks /query`；`watchdog-state.json` 的 `checkedAt` = 02:48:53 |
| Mini App 运行时 | **活着**：`duty-heartbeat.json` 02:48:41 刚写过（60 秒心跳） | 板面状态文件 mtime |
| 看门狗**会不会报警** | **不会** | `alertable = stale && mode !== 'resting'`；`duty-intent.mode = resting` → 恒为假 |
| 值班 cron `2a1d79e8` | **调度 job `cancelled`**，`next_run_at_ms = null`，`run_count = 12`；定义本身 `deleted_at_ms = null`（还在） | `local_runtime_v2_scheduler_jobs` / `local_runtime_v2_cron_definitions` |
| 最后一次 cron 成功投递 | **2026-10-27 13:07** | `local_runtime_v2_cron_runs` |
| 此后空槽 | **219 个**无人值班 | `duty-heartbeat.json` 的 `blankTail.slots = 219` |
| 心跳补偿 | **锁死**：`reason = already_triggered`（槽位 330 已补过）→ 不会自己再补 | `duty-heartbeat.mjs` 的判定分支 |

| 管辖名单 | **只有 1 项**：`Mimic Tear`（projectId 256），理由是大老板 2026-10-27 的原话 | `managed-projects.json` |

**两条从这些读数里长出来的判断**：

1. **「持久」这条特征目前是靠"不报警"维持的，不是靠"能恢复"维持的。** 看门狗活着、心跳新鲜、任务 `Last Result = 0`——所有健康信号都绿，但**没有任何一个组件在替大哥兜底**，因为 `resting` 让告警恒关。这是既定设计（「休息不是故障」，主规格 §27.6），不是缺陷；**但它把一个前提变成了硬依赖：大哥醒来的那一天，一切是从零开始的。**
2. **219 个空槽 + 心跳补偿锁死，构成一条断掉的恢复路径。** 大老板哪天说「大哥，上岗」，恢复的不是「从上次继续」，而是「补 219 轮的空档」——而心跳补偿因为 `already_triggered` 锁死，**不会自己再补**。这条要在动手做任何新东西之前先说清楚（G-10）。

### 2.6 上下文边界与多实例（文章 §8.3）——**已有，且明确不做 A2A**

文章 §8.3 说：组织「在决定如何配备 Super-agent 时实际上是在划分上下文共享与隔离的边界」，需要共享的共用一个实例。

我们的**管辖名单**（`managed-projects.json`）**正是这个边界**：名单内的项目共享大哥这一个实例的上下文，名单外的一概不派工、不恢复、不催办（主规格 §22.2，`:1558`-`:1568`）。这是**直接命中，不是缺口**。

文章 §8.3 后半段的**多实例 A2A**（多个彼此隔离的实例互通信）**我们明确不做**——理由见 §5。

### 2.7 文章没有覆盖、但必须留在我们这边的东西

文章谈的是「让一个 agent 持续在线」，没谈「agent 怎么沉淀自己的能力」。我们有两处是文章里没有的，对齐时**不要顺手删掉**：

| 我们的东西 | 现状 | 文章里的对应物 | 决定 |
| --- | --- | --- | --- |
| **技能库（注册表 + 匹配 + 退役）** | `skill-library.json`：`version` / `updatedAt` / `entries`；四态 `candidate` / `active` / `stale` / `retired`；**3 条 `active`，`usageCount` 全为 0** | 无。文章的 Router 是「按类型选 agent」（§2.1），技能索引不在它的五模块里 | **保留**。但 `usageCount` 全 0 说明匹配路径**没有任何使用痕迹**——这是「技能库建好了却没人用」的一个实证，不是架构问题，列入 G-11 |
| **技能工厂（从执行中提炼技能 → 协调封装 → 注册 → 派工时匹配 → 定期校验退役）** | 大哥的第四项职责；五铁律在 `mimic-tear-skill-forge` 技能里 | 无 | **保留**，且它是文章 §3.4 投机执行的一个天然落点：大哥在执行中识别到的重复模式，正是技能的原料 |

> **这一节的作用是防止误伤。** 未来照着文章做对齐时，很容易把「文章里没有的东西」当成「多余的」。技能库与技能工厂不在文章的五模块里，但它们是大哥区别于「一个总管」的地方——**去掉它们，大哥就退回成一个派工中间人**。

## 3. 四特征自评

判据都写成**可测**的形式，不写成形容词。

### 3.1 连续（Continuity）

| 项 | 内容 |
| --- | --- |
| **判据** | 同一件事在任一入口继续讨论，大哥能接上上下文，**不要求用户复述**；跨线（不同项目）之间的信息也能被找回 |

## 5. 明确不照搬的部分

文章是**为「云端 + 多信道 + 跨设备 + 团队规模」写的**。我们是**本地 + 单宿主 + 单人 + Mini App**。照搬会引入我们自己付不起的代价。这一节是本文的**否决清单**——写下来是为了让将来的人**不要**再把文章当成待办清单逐条实现。

| 文章的做法 | 我们的情况 | 决定 |
| --- | --- | --- |
| **云端无状态计算容器 + 数据库存会话状态**（§5.1） | Mini App 跑在桌面端宿主进程里；运行时库就在本机 | **不照搬**。存算分离解决的是「跨设备持久在线」，我们的持久性瓶颈是「宿主进程会停」，两件事的解法不同。我们已经在本机做到了等效的事：大哥跑在 OS 计划任务里，板面开不开它都在 |
| **端侧轻量 daemon（BYOM）接入远端执行环境**（§5.2） | 只有一台机器，执行环境就是它自己 | **不照搬**。要 daemon 就得跨进程接管命令执行与凭据，等于自己重写一套工具链——而我们现在直接用 `mavis session send`，能力已经够了 |
| **IM / GitHub 多信道接入**（§4.2） | 只有板面 + 宿主侧栏两个本地入口 | **不照搬接入方式**，但**照搬带宽纪律**：「单次回复不超过 100 词」「只问直接问题、给简短结论」——这条对板面结论同样成立 |
| **Router 层水平切分 / sharding**（§2.1 尾、§8.1） | 单个大老板，量级几十个会话 | **不照搬**。文章自己说「在全局记忆问题被解决之前，这一权衡始终存在」——我们连短程记忆都还没有，现在切分等于把连续性提前丢掉 |
| **跨实例 A2A**（§8.3） | 单实例 + 管辖名单已经划好了边界 | **明确不做**。要做的前提是多个彼此隔离的实例，现有形态里不存在这个需求 |
| **模型与系统的协同设计（Co-design）专项训练**（§8.1） | 我们不训模型 | **不照搬** |
| **跨月长程记忆**（§8.1 末） | 文章自己列为开放问题 | **搁置**。先做链式召回的短程版（G-05）；长程记忆在链式召回稳定之前做，只会更早地变成噪声 |

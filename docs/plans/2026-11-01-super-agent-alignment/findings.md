## 计划级决策

### F0.1 · 现在不开 worktree

**问题。** `module-planning-with-files` 的约定是「每个 plan 开一个自己的 worktree 与分支」。本计划落地时照做即可——但**这份计划文档本身**要不要现在就把仓库切到一个新 worktree 去写？

**结论：不切。** 计划的三份文档写在当前工作树里，作为一次普通的文档提交（走 PR）。worktree 与分支在 **Phase 1 真正开工时**创建，从当前 `main` 切出。

**否掉的替代方案：立刻开一个空 worktree。** 它有一个真实的好处——不弄脏主工作树。但代价比好处大：仓库里现在有另一个 agent 的在制品（`git status --short` 在写文档前是干净的，但 `Saved/` 下有未跟踪的诊断产物），切分支的动作本身会让「谁的改动」变模糊，而本仓库的提交纪律（`docs/plans/2026-10-22-line-ownership.md` §3）正是为了避免这个。**为三份文档切分支，是把纪律用在没有风险的地方。**

**代价。** 计划文档本身没有独立分支保护。接受——文档提交是低风险、可回滚的，且走 PR。

## Slice 1 — 让大哥能安全上岗

### F1.1 · 一趟覆盖整段空档，不采样、不逐槽

> **2026-11-01 修订**：这一条原来是「按固定间隔采样代表槽位（约 9 轮）」。读代码之后发现那是错的，
> 改成「一趟覆盖整段尚未覆盖的空档」。理由见下面的「为什么原方案错了」。

**问题。** 大哥自 2026-10-27 13:07 之后没跑过 cron，留下 **219 个空槽**（`duty-heartbeat.json` 的 `blankTail.slots`）。恢复时这些槽位要不要一个个补、补多少？

**结论：一趟覆盖整段尚未覆盖的空档。** 一次补位就是一轮值班巡检，它看的是**当前**状态；断档 219 轮不等于要跑 219 遍——跑 219 遍只会得到 219 条几乎一样的结论，而收件箱已经堆了 93 条没人看的（基线规格 §2.2.1）。补完之后把「覆盖到第几槽」记下来；只有当空档**继续往前推进**（新槽位出现）时才再补下一次。

**为什么原方案错了。** 原方案假设「空槽会被逐槽补齐，所以要采样来控制数量」。读完 `duty-status.mjs` 的 `computeDutyEvidence` 才发现：空槽的起点永远是「最后一次成功投递之后的第一格」（`slotOf(lastDelivered) + 1`），而心跳补位**不会在调度器的运行记录里留下任何东西**——所以那一格永远不会往前挪。**旧实现的锁不是「记错了」，是结构性的：心跳整条链路只能补一次。** 在这个前提下讨论「采样几轮」是没有意义的，因为根本没有「逐槽补齐」这条路径存在。

**否掉的替代方案：逐槽全补。** 它的优势是不丢信息，但代价是 219 轮 × 每轮一次 LLM 推理——按一次巡检 20 秒算也要 73 分钟，而它补出来的 219 条结论里绝大多数是「和上一轮一样」。**218 条重复结论换 73 分钟，正是收件箱变成垃圾堆的成因。**

**否掉的替代方案：采样补齐（原来的方案）。** 它比逐槽全补省，但仍要跑 9 轮 LLM，产出 9 条高度相似的结论，而补的内容**和跑 1 轮完全一样**——因为巡检看的是现在，不是过去。省下的不是成本，是没必要的重复。

**否掉的替代方案：整段跳过，只报时长。** 最省。但断档期里真正发生的事（会话报错、问卷卡积压）就此消失，而那正是大老板最需要知道的。一趟覆盖是这两者之间：**状态是当下的，所以一趟就够；缺口要说清楚，所以时长必须如实报。**

**代价。** 断档期的细节不完整——摘要里必须写明「补的是当前状态，不是重放那几轮」。**这个「不完整」要写进摘要和提示词，不能只在代码注释里。**

### F1.2 · 覆盖标记要能前进；「解除锁死」变成「按需重新覆盖」

**问题。** 心跳补位失败时，旧实现把那个槽位记成「已补」，于是**这一段永远不再试**；补位成功时，覆盖标记又锁在那一格不动，整条链路只能补一次。

**结论：记「覆盖到第几槽」，失败不推进覆盖标记。** 覆盖标记是单调的——新空出来的槽位号更大，覆盖标记自然落后，缺口就露出来了。补位失败时**不推进**覆盖标记，下一跳可以重试。

**「显式解除」还在，但角色变了。** 它不再叫「解除锁死」（锁已经不死），而是 `patrol-cli gap reset "<理由>"`：**按需重新覆盖整段空档**。理由必填，因为它是一次决定——而自动解除就等于把「自动补位会出事」那个坑重新打开。

**否掉的替代方案：保留旧的「记刚补的那一槽」写法，只加一个过期时间。** 看着更小改动。但它治的是症状：那一格永远不挪，所以「过期」也救不了它——过期之后重新锁回同一格，还是补不了下一格。**记错了的东西不会因为加个时钟而变对。**

**否掉的替代方案：把补过的槽位写回调度器的运行记录。** 那才是「真的补过了」的终态。但运行时库**只读**（主规格 §3.3），这是一条不可协商的硬约束。覆盖标记只能住在插件自己的状态里。

**代价。** 插件状态里多两个字段（`coveredThroughSlot` / `coveredAt`），并多一条「失败不推进」的规则要守住——后者用变异验证证明过（把覆盖推进挪到失败分支之前，测试立刻变红）。

### F1.3 · 上岗摘要给大老板看，不是给大哥自己看

**问题。** 「断了多久、这段时间发生了什么」这个信息，给谁？

**结论：给大老板。** 做成板面上的一段可读摘要（在收件箱顶部，不是一条待办）。大哥自己看到的内部形态可以不同——它需要的是「我不在的时候哪些线断了」，但**那是派工上下文，不是给人看的汇报**。

**否掉的替代方案：给大哥一份「交接文档」再让它自己总结。** 这是 `DUTY-HANDOFF.md` 现在的做法（47890 字节，2026-10-30）。它的问题是：**大老板仍然要看大哥写的总结**——而大老板要的是「我的项目怎么样了」，不是「大哥的工作日志」。让大哥写、再让人读，等于没省掉任何一层。

**否掉的替代方案：把摘要做成收件箱里的一条普通结论。** 那它就会和那 93 条未确认的结论混在一起——**最需要被看到的东西，埋在一堆没人看的里面**。摘要的位置必须固定在收件箱顶部。

**代价。** 多一个专用呈现位。接受。

### F1.4 · 动手时才发现的三处根因（都不是「缺个功能」，是「结构错了」）

**问题。** 原计划把 G-10 理解成「补一个恢复入口」。读代码才发现，恢复不了的根因有三处，而且**没有一处是「少了个功能」**：

1. **覆盖标记是死的。** 空档起点恒等于「最后一次投递之后的第一格」，补位又不会在调度器记录里留痕，所以那一格永远不挪 → 心跳整条链路只能补一次。
2. **补位失败等于永久锁死。** 失败那轮被写进状态（`lastTriggeredSlot = 那一槽`），下一跳读到的还是同一格 → 判成「已触发」→ **永不重试**。
3. **休息期间照样补位。** 心跳**从不读**值班意图，所以被交代去休息的大哥照样被派值班轮次——只是因为第 1 条的锁，它碰巧没发作。**换句话说：那把锁在替一个它不该替的岗。**

**结论：三条一起改。** 新增 `duty-gap.mjs` 承担空档判定（洞 vs 漏班），心跳改成记「覆盖到第几槽」、失败不推进、休息不补。

**否掉的替代方案：只补第 1 条（让锁能解开）。** 那样大哥上岗后仍然会在第一次补位失败时永久卡住，而且休息期间照样被派值班轮次——**一个只解开一半的恢复路径，比不解开更危险**：它看起来能用了。

**否掉的替代方案：把「休息」也做成锁的一部分（休息时锁住，恢复时解锁）。** 那要额外存「休息前锁在哪」，而且休息期间空槽还在涨——醒来时那把锁指的位置已经过期了。**读值班意图更简单也更准**：休息是一个当下的事实，不是一段历史。

**代价。** 心跳第一次真正读 `duty-intent.json`——这是它第一次把「用户说大哥在休息」当成输入，而不是只在看板的告警判定里用到。**这条依赖是单向的**（心跳读意图，不写意图），所以不会反过来影响用户的选择。

## Slice 2 — 事实层：Trigger 与两级过滤

### F2.1 · Trigger 由 Mini App node 侧生成，不写进运行时库

**问题。** Trigger 是什么、存在哪？运行时库里有 `local_runtime_message_rows`（消息行）、`local_runtime_v2_cron_runs`（cron 运行）等表，但它们**不是**我们的事件模型——而且运行时库是**只读**的（主规格 §3.3）。

**结论：Trigger 由 Mini App node 侧生成**，形态是「从运行时库的变化中**识别**出来的、带 ID 与摘要的事件对象」；**不新建运行时表，也不往运行时库写任何东西**。触发源按主规格 §2.1 的已验证数据源逐个接：项目状态变化、问卷卡、会话异常、cron 唤醒。

**否掉的替代方案：往运行时库里加一张 `triggers` 表。** 它会让事件的产生与消费都在运行时里，理论上更「原生」。但：① 违反只读硬约束（主规格 §3.3）——那是一条**不可协商**的硬约束；② 插件的自建状态已经有明确归属：`context.dataDir`。

**否掉的替代方案：直接拿 `local_runtime_message_rows` 当 Trigger。** 它确实已经是「环境事件」，省一套抽象。但它记的是**消息投递**，不是**环境状态变化**——会话在跑但没人说话时它没有记录；项目健康度变化时它也没有记录。而「主动」要的就是后者。

**代价。** 需要一层「变化检测」（轮询 revision / `PRAGMA data_version` / 消息条数）——主规格 §23.3 已经有一个这样的检测器（`chatHistoryChanged`），可以复用同一套思路。

### F2.2 · Fast Path 的准入判据写在代码里，不写在提示词里

**问题。** 文章 §3.1 的两级过滤，第一级是**程序策略**（Fast Path），第二级才是模型判断（Slow Path）。我们的等价物是：管辖名单匹配 + 事件类型白名单。**这一级写在哪？**

**结论：写在代码里。** `candidates` 的产出是 `facts` 的一个**确定性**子集——同一个输入永远得到同一个输出。名单外的项目，**在任何情况下**都不进 `candidates`，无论提示词怎么写。

**否掉的替代方案：只写在提示词里，让模型自己判断「这属于我管的项目吗」。** 更省事，而且「模型判断」听起来更聪明。但主规格 §22.3 已经**实测过**提示词会互相覆盖（「昨晚 23:59 大哥改了 cron，00:03 我改，结果大哥的版本把我的管辖范围两节冲掉了」）。**管辖权这件事已经用一次事故证明过：它不能只活在提示词里。** 程序层过滤是同一原则的延伸。

**否掉的替代方案：Fast Path 和 Slow Path 合并成一件事，全交给模型。** 就是今天的现状。代价是可测的：每轮把全部事实灌进模型，噪音占比随项目数线性上升。

**代价。** 事件类型白名单要人工维护；新增事件类型时忘了加，**它会被静默丢弃**。缓解：白名单的每一项都要有单测，且**新增类型必须显式改代码**（漏了会红，不是漏了会静默）。

### F2.3 · `facts` 双段输出，模型默认只看 `candidates`

**问题。** `facts` 现在是一个大对象，装着全部项目、决策、问卷、可恢复会话、Goal、已报过的事。Filter 之后，如果 `raw` 还在同一个输出里，模型很可能还是把全量读了——**过滤就白做了**。

**结论：双段输出，但 `raw` 默认不给模型。** `facts --scope=candidates` 是给模型的默认视图；`raw` 只在明确请求时展开（`facts --scope=raw`），并**计入一个显式的「我主动要了全量」的信号**。

**否掉的替代方案：单段输出，过滤在模型提示词里做。** 等于没有 Fast Path。见 F2.2。

**否掉的替代方案：把 `raw` 删掉，facts 只出 candidates。** 最干净，但**诊断会瞎**——出问题时没有全量视图可看，等于把排查工具一起删了。

**代价。** 多一个 `--scope` 开关和两种输出形状，测试要覆盖两遍。接受——诊断能力不能省。

## Slice 3 — 直通：Thread 与订阅

### F3.1 · 一条线 = 一个管辖项目 = 一条 Thread

**问题。** Thread 是什么粒度？文章 §3.2 说的是「同一个 PR、同一个 IM 话题、同一封邮件串」——在 GitHub/IM 的世界里那是**很细**的粒度。

**结论：一条 Thread = 一个管辖项目**，其项目根会话为负责方。粒度粗得多，但对我们是对的：我们的「环境」是项目，跨项目的事件流在运行时里本来就没有可靠的关联。

**否掉的替代方案：按会话粒度（一个根会话 + 它的子会话 = 一条 Thread）。** 更贴近文章，粒度更细。但我们这里**一个项目常常只有一个根会话**，会话粒度与项目粒度在多数情况下重合——细分下去只会让订阅表变复杂，没有换来新能力。

**否掉的替代方案：按「事件类型」分 Thread（一条线上同时有代码事件、问卷事件、异常事件）。** 这是**多对多**订阅的形态，文章 §3.2 支持它。但我们**先不做**：多对多意味着「一条线上有 N 个 Worker 同时被叫醒」，而我们连单订阅的投递可靠性都还没验过（`session send` 的两条硬限制：排队≠已执行、goal 链会饿死排队消息，主规格 §3.5）。

**代价。** 同一个项目的不同类型事件会被合并成一条线的上下文。**在当前规模下这是优点不是缺点**——人一次只能跟 3 到 5 条线（文章 A1）。

### F3.2 · 直通用 `session send`，不发明新投递机制

**问题。** 直通要把事件送到负责会话。用什么送？

**结论：用现成的 `mavis session send`。** 它是运行时已有的投递机制，我们**已经**在用它派工（主规格 §3.3），而且它的两条限制我们已经踩过并写进了规格（主规格 §3.5）。**复用一条已知有边界的能力，好过发明一条没边界的新通道。**

**否掉的替代方案：新增一个 Mini App 侧的「直通投递」端点，由 node 服务直接写运行时库。** 更快、更可控。但那**违反只读硬约束**——主规格 §3.3 已经把「直接写运行时库」的路径逐条测过并否掉了（写 `reply_payload` 运行时根本不轮询）。

**否掉的替代方案：走 `context.agent.run` 起一个新会话。** 那是**新建 Worker**，不是直通。直通的前提是「已经有一个上下文在那儿」，起新会话恰好丢掉了这个前提。

**代价。** 直通继承 `session send` 的全部限制，包括「目标在跑 goal 链时排队消息永远不执行」。**这不是新问题，但直通会放大它**——因为直通是高频的。所以 F3.4 的降级记录必须可靠。

### F3.3 · 直通永远不越过管辖名单

**问题。** 直通是程序行为，不由模型判断。那它会不会把事件送进名单外的项目？

**结论：不会。** 直通只对**已建立订阅**的 Thread 生效，而订阅**只能由大哥在管辖名单内的派工建立**。名单外的项目**没有订阅表项**，直通对它**没有任何路径**。名单是**结构性**的闸，不是运行时的一次判断。

**否掉的替代方案：直通用提示词约束「不要送名单外的」。** 主规格 §21 的那起越权事故就是这个思路的反面教材（「待大老板定」被读成「由你定」）。**管辖权必须是状态，不能是提示词**（主规格 §22.3）。

**代价。** 新增一条线要走「大哥派工」这条路，不能由系统自动建立订阅。这是**有意的摩擦**。

## Slice 4 — 产出收敛与低打扰

### F4.1 · 收件箱上界按「需要你拍板」定义，不按条数

**问题。** 收件箱有 100 条结论、93 条未确认。**上限该怎么定？**

**结论：语义上界。** 只有**需要大老板拍板**的才进收件箱；其余（已汇报过的进展、可以自决并已自决的事、重复的同一件事）进**可查的流水**，不进收件箱。再加一个可配置的条数兜底（防语义判定失效时无限膨胀）。

**否掉的替代方案：纯条数上限（比如最多 20 条，超了挤掉最旧的）。** 实现简单，但**挤掉最旧的等于删结论**——主规格 §19.5 已经确立了「撤回过的结论仍然留着」这条规矩，同理，**被别的结论挤掉的结论也应该还找得到**。

**否掉的替代方案：保留全部，但按严重度排序、默认折叠。** 保留信息最多。但**93 条折叠着的结论仍然是 93 条**——大老板仍然要面对一个「看起来有 93 件事」的界面，而判断「哪几条需要展开」这件事本身就要花注意力。

**代价。** 语义判定比条数判定复杂，且**判定会出错**。缓解：判定在程序层做**明显的**那部分（`severity` 字段 + 是否需要决策的显式标记），拿不准的一律进收件箱（**宁可多，不可漏**）。

### F4.2 · 93 条历史结论归档，不删除

**问题.** 那 93 条未确认的结论怎么处理？

**结论：归档。** 移进一个可查的归档区（带时间戳与归档原因），**不删**。归档动作本身要在收件箱留一条记录。

**否掉的替代方案：直接删。** 干净。但这些结论里有**大老板当时没来得及看的信息**——删了就永远没了，而「没看」不等于「不重要」。

**否掉的替代方案：原样留着，只是折叠。** 见 F4.1——那不解决 93 条的问题。

**代价。** 板面多一个归档入口。接受。

### F4.3 · 单条结论 ≤ 100 词，做成断言

**问题.** 文章 §4.2 给了 IM 信道的硬规矩：「单次回复不超过 100 词」。我们要不要抄？

**结论：抄。** 但**落到板面结论**上，不是 IM（我们没有 IM 信道）。做成**代码里的断言**，超过就红。

**否掉的替代方案：不抄，靠提示词里的「简洁」两个字。** 主规格 §3.5 那条铁律是「两份文本要同步」——提示词里的措辞会被改、会被覆盖、会被另一个 agent 的版本冲掉（§22.3 的事故）。**能用断言守的，不要靠措辞。**

**否掉的替代方案：抄了但不落断言，留给未来的人自觉。** 那这条规矩和没抄一样。

**代价。** 词数怎么算（中文按字还是按 token）需要定死，并且**这个定义本身会成为后续争论的战场**。缓解：先按最保守的算（中文按字、英文按空格分词），实现简单。

## Slice 5 — 线视角的板面

### F5.1 · 「线」= 一个管辖项目 + 大哥在这条线上的作为 + 待你决策的事

**问题.** 板面从「按项目」改成「按线」，线是什么？

**结论：线 = 一个管辖项目**（与 Thread 一一对应，见 F3.1），加上两样东西：**大哥在这条线上的作为**（最近做了什么）与**待你决策的事**（这条线上挂着的待答项）。

**否掉的替代方案：线 = 大哥手头的差事（一次派工 = 一条线）。** 更贴近「活」的粒度。但那会让同一个项目在多条线上重复出现，而大老板的心智模型是**项目**（板面 §6.1 现在就是这么组织的，文章 §8.2 说这可能是路径依赖，但我们换不掉用户的习惯成本之前不该换）。

**否掉的替代方案：线 = 大老板的一个目标（跨项目）。** 这是文章 §8.2 暗示的方向（「交互可能更多发生在领域特化的界面里」）。但我们**没有目标层的数据模型**——`managed-projects.json` 是项目粒度，跨项目聚合要先有「目标」这个实体。

**代价.** 线比项目多两样东西（作为、待决策），数据要能从 Thread 状态和收件箱条目里聚合出来。

### F5.2 · 旧的按项目总览保留为下钻，不做第二套总览

**问题.** 改版之后，旧的「逐项目一张卡」的总览还留不留？

**结论：保留为下钻层。** 新的总览是「我的一个大哥 + N 条线 + K 件等你拍板」；点某条线进去，仍能看这个项目的原有卡片。**不做第二套总览。**

**否掉的替代方案：两套总览并存，用户自己选。** 看似尊重用户，但**两套总览就是两份口径**——这个仓库已经因为「多处口径不一致」吃过亏（主规格 §25.1：三处口径不一致，判据必须只有一个）。

**否掉的替代方案：彻底删掉按项目的视图。** 干净，但**把一个能用的东西删掉，换一个还没验证的新东西**——而且现在的下钻信息（项目详情视图）本身是有价值的。

**代价.** 两套视图的数据要一致，改动时容易只改一套。有测试守住（客户端契约测试已经逐个钉住端点）。

## Slice 6 — 韧性：判进展、全双工、状态收口

### F6.1 · 「实质进展」用确定性判据，不用模型判

**问题.** 文章 §6 的 Watchdog「会由模型判断各个 Worker 是否有实质进展、方向是否偏离整体目标」。我们要不要用模型判？

**结论：不用。先用确定性判据。** 「目标会话近期是否有产出增长 / 状态迁移 / 新产物」是可以写成纯函数并单测的。模型判留作**升级项**，不是第一版。

**否掉的替代方案：一上来就用模型判（照抄文章）。** 它的表达力更强——「方向偏离」确实只有模型能判。但：① 引入一个**不可测延迟**的判定环节，而判定要喂给一个「该不该叫人」的决策；② 出问题时无法复现；③ 这个仓库的一条既有原则是「判定逻辑必须只有一份」（主规格 §17.2），再加一个模型判定就多了一个说不清行为的判据。**先用确定性的，把「偏离」留给下一版。**

**否掉的替代方案：沿用现在的只看心跳。** 最省。但那正是文章 A10 点名的盲区：**「许多异常并非进程崩溃，而是模型在执行中陷入无效循环或偏离目标」**。心跳新鲜、进程活着、实际在空转——现在的看门狗全绿。

**代价.** 「方向偏离」这类异常要等下一版才覆盖。**明确写进已知限制，不假装覆盖了。**

### F6.2 · 值班轮次改异步语义，但不重写 ReAct Loop

**问题.** 文章 §4.1 要的是全双工：模型调 `start()` 立即返回，后台跑，结果作为新事件投回来。

**结论：做 `start` / `stop` 语义，但只作用在「巡检轮次」这一层。** 轮次变成可异步起停的；新指令**不排队等轮次结束**。**不重写整个 ReAct Loop**——我们没有自己的 Loop，Loop 在宿主运行时里。

**否掉的替代方案：让整个值班会话变成多线程 / 多轮并行。** 那是宿主运行时的能力，不在我们手里。我们能控制的是「大哥这一轮做什么、怎么收尾」。

**否掉的替代方案：只加一个「打断」按钮（`force_steer`）。** `force_steer` 已知会**打断对方正改一半的文件**（主规格 §3.5），拿它做值班插话的默认手段太危险。

**代价.** 异步轮次要处理「轮次还在跑时又来一条指令」的竞态。缓解：轮次有明确的 `slot` 标识，重复轮次直接跳过（这跟心跳补偿的 `slot` 机制是同一套思路，可以复用）。

### F6.3 · 状态收口到一个 store，但**不建数据库**

**问题.** 文章 §5.1 主张「状态进数据库、计算无状态」。我们的板面状态散在 `liveboards/mimic-tear/` 下的十几个 json 文件里。

**结论：收口到一个带版本号的原子写 store**（沿用现有 `json-ledger.mjs` 的做法：唯一临时名 + 读-改-写 + 跨进程锁 + rename 后自检）。**不建数据库**——仓库的硬约束是零第三方依赖，而 Node 内置的 `node:sqlite` 虽然可用，但它会把「插件自建状态」变成「插件自建数据库」，与主规格 §2「**不引入任何自建状态库**」直接冲突。

**否掉的替代方案：用 `node:sqlite` 建一个插件状态库。** 事务能力更强。但**主规格 §2 的结论是「运行时已经是唯一数据源，架构不引入任何自建状态库」**——插件自建状态只写在 `context.dataDir` 里，这是硬约束。

**否掉的替代方案：不收口，让各文件各自负责。** 零成本。但**跨文件一致性问题已经出过真事故**——派工账的并发写毁掉记录（`docs/2026-10-28-optimization-recommendations.md`「本轮顺带抓出来的两个真缺陷」第 1 条：幂等键就在账里，丢一条就可能把同一条指令重投一次）。收口是为了让这类问题**只剩一处**。

**代价.** 收口是一次**有风险的重构**——它动的是所有状态的读写路径。必须**一个字段一个字段迁**，每迁一个跑一次全量测试，且**保留旧文件的读取兼容**一段过渡期。
